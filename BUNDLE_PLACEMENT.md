## 1. Scope and ground rules

- **DECIDED** -- Skeleton first: bundles and transitions are created and made to work with NO wires involved. Wires are routed onto the skeleton afterwards (`BUNDLE_DESIGN.md` 2.7).
- **DECIDED** -- 3D view first; the peg-board view gets its own placement behavior afterwards. Bundles and transitions are never shown in the schematic view.
- **DECIDED** -- A bundle (and a transition) is ONE object that exists in both the 3D and the peg-board view. Its waypoints and layouts are independent per view (different counts, different positions), stored per view in `pjt_bundle_paths`.
- **DECIDED** -- Pre-release: no data migration, no backwards compatibility. All existing bundle and transition code has never been run; it is a draft, not a constraint.
- **DECIDED** -- The toolbar "Add Bundle" button stays, and now places a free bundle.
- Bundle placement uses the cover part chosen in the DB editor, or the part-search dialog if none is selected (as `Bundle.start_add` does today).

## 2. Terms

- **Skeleton:** the bundles (edges) and transitions (nodes) of a harness, without any wires.
- **Free end:** a bundle end that is not attached to a transition.
- **Free branch:** a transition branch with nothing attached.
- **Terminus:** a free bundle end or a free transition branch -- a place a wire can later enter or leave.
- **Attach:** a bundle end and a transition branch position become the SAME point row (in each view), so they move together.

## 3. Bundle placement

- **DECIDED (user, 2026-09-26) -- placement interaction in 3D:**
  - **First left click:** places the bundle's start point (free, or snapped to a free transition branch, see below).
  - **Second left click:** places a bundle LAYOUT (an interior waypoint marker) at that point. Every further left click places one more layout, each extending the bundle by another section. A live preview section follows the mouse from the last point.
  - **Right click after only the first click:** the whole placement is canceled (no bundle is created).
  - **Right click after the second or a later left click:** the placement of the NEXT section is canceled but everything up to that point remains; the last layout is removed and its point becomes the bundle's END point. (So click, click, right-click = a one-section bundle with no waypoints; click, click, click, right-click = one waypoint.)
  - **Clicking on a transition branch** (at any click after the first) connects the bundle to that branch and ENDS the placement; the branch position becomes the bundle's end point (attach, section 5, subject to the diameter-range rule).
  - The existing wire handler already works this way (`add_handlers/editor_3d/wire.py`: growing point, commit waypoint, `_promote_last_committed` turns the last committed waypoint into the end point), so it is the model to follow. Escape/cancel key behavior is not specified by the user.
- **DECIDED (user, 2026-09-26)** -- The FIRST click of a bundle can either be a free placement or be snapped to a transition branch (a free branch). A snap is only allowed if the bundle's minimum and maximum diameters will fit the branch's minimum and maximum diameters: there MUST be an overlap between the two ranges (user wrote "overlay"; read as overlap: `max(min_bundle, min_branch) <= min(max_bundle, max_branch)`).
- **DECIDED (user, 2026-09-26)** -- The bundle's initial diameter: snapped to a branch = `max(min bundle, min branch)`; free click = the bundle's minimum diameter. (There are no wires to size it; concentric packing comes later, see `BUNDLE_DESIGN.md` phase order.) The bundle starts EMPTY.
- **OPEN** -- The SECOND click (the stop end) snapping onto another free branch: a bundle has only one diameter, so it must lie in the overlap of the bundle's range with EVERY branch it is attached to. Suggestion: the snap is only allowed if the ranges of the bundle, the first branch (if any) and this branch all still overlap, and the diameter is raised to the overlap's lower bound if needed (`max` of all the minimums).
- Interior waypoints can ALSO be added after placement from the bundle's context menu ("Add Handle"), as the existing code does.
- **PROPOSED** -- While placing, either end snaps onto a free transition branch position (attach, section 5), subject to the diameter-range rule above. It does not snap onto anything else (no snapping onto other bundle ends or mid-bundle).
- **PROPOSED** -- A newly placed bundle also gets its peg-board start/stop points (section 6), otherwise they would auto-create at (0, 0, 0) and the bundle would be degenerate in the peg-board view.
- The existing wire-snap flow (`Bundle.start_add` in `objects/objects_3d/bundle.py` plus `add_handlers/editor_3d/bundle.py`, which picks a wire and spans it end to end) is REPLACED.

**IMPLEMENTED (2026-09-29).** `Bundle.start_add` (toolbar) and the new `add_handlers/editor_3d/bundle.py` `Bundle` class implement every DECIDED rule above end to end: phase 0 (start point, free or branch-snap) / phase 1 (growing stop, one section per click, click-a-branch-to-attach, right-click cancel-or-promote-last-waypoint) exactly mirroring `add_handlers/editor_3d/wire.py`'s own state machine, real ray-sphere branch hit-testing across every transition in the project (`handlers/transition_handler.py`'s new `_find_free_branch_ray`, reusing `RouteThroughTransitionHandler`'s existing `_BRANCH_FIT`/`_BRANCH_NO_FIT` highlight materials), and the section 5 hard rule (a branch attach excludes every OTHER branch of that same transition from the other end's own hover). The OPEN second-click-diameter question above is resolved as suggested: a session tracks `(diameter_lo, diameter_hi)` starting at the cover part's own range, narrowed (raised lower bound, tightened upper bound) by each branch attach, so a second attach is only offered when it still overlaps whatever the first one already narrowed to; the final diameter is always the narrowed lower bound, and every attached branch's own diameter (`Branch.set_diameter`) is kept in sync with it. Every branch attach also drops a `BundleLayout` marker exactly on the shared joint point (its own diameter/color derive automatically from the newly-attached bundle, `PJTBundleLayout.attached_bundles`) -- fixed a real, previously-latent `IndexError` this surfaced in `objects_3d/bundle_layout.py`'s own diameter derivation (a skeleton bundle with no wires yet has no concentric layer at all; fixed by preferring the live bundle object's own already-cached diameter when one exists). `objects_3d.bundle.Bundle.start_add_from_branch` (the branch context-menu entry point, see `TRANSITION_DESIGN.md`) now shares this exact same session class and its real attach path instead of a second, separately maintained one -- it just pre-seeds phase 0's hover state and replays `_handle_first_click` synthetically before the user's first real mouse move.

Peg-board seeding (the last PROPOSED bullet above) is also implemented, but only to the depth section 10's own implementation order calls for at this stage ("with peg-board start/stop seeded") -- see that section's own updated entry for what it does and does not yet handle (the length-preserving unfold is exact for a free/free or free/branch bundle; a bundle pinned at both ends can still end up with a peg-board length that doesn't quite match its 3D one, left for the peg-board chain solver, section 6b, not built yet).

## 4. Transition placement

- **DECIDED (user, 2026-09-26) -- free placement:** a transition can be placed freely, with nothing attached. In this case the 3D position seeds the peg-board position (the x/z projection at y = 0, as a housing does -- a transition has no length to preserve, so the projection is fine here).
- **DECIDED (user, 2026-09-26) -- placement at the end of a bundle:** a transition can be placed at the end of a bundle. When this is done the transition is placed so that ALL of its branches can be seen, and the user then SELECTS the branch they want to attach to the end. The transition is then placed and rotated, if necessary, so that the chosen branch connects to the bundle end FORMING A STRAIGHT LINE (the bundle's last section and the branch's axis are collinear: the branch's outward axis points back along the bundle, so the bundle runs straight into the branch mouth).
- **DECIDED (user, 2026-09-26) -- one connection at placement time:** at transition placement time we only ever handle making the ONE connection (the branch chosen at the bundle end). Other bundles are connected to the remaining free branches later, by drag and drop.
- **DECIDED (user, 2026-09-26) -- no mid-bundle placement:** a transition is never snapped onto the middle of a bundle (and the old wire-first behavior of splitting/shortening a bundle at the snap point is removed). To put a transition in the middle of a bundle, the bundle is first SPLIT into two bundles (section 4c), then the transition is placed at one of the resulting ends.
- **PROPOSED** -- All wire assignment is REMOVED from placement: no assigning a bundle's wires to output branches, no creating new wire rows, no per-branch concentric from wires. A new transition has all branches free.
- **PROPOSED** -- The user picks the branch by hovering (the branch under the cursor highlights) and clicking; right click cancels the placement. Branches whose diameter range does not overlap the bundle's cannot be chosen (shown disabled), by the same overlap rule as bundle placement. **OPEN** -- confirm the interaction; and the transition's roll about the branch axis (the transition body lies in its local plane): suggestion, keep that plane horizontal (world up) where possible and let the user rotate afterwards with the existing rotation gizmo.
- **OPEN** -- Orientation of a transition placed in free space (default angle, rotate afterwards with the existing gizmo?).
- A transition's shape and branch positions come from its global catalog part (each branch has an index, angle, length, offset, bulb size, min/max diameter); branch positions are stored as `pjt_points3d` rows in world space and derived from the transition's position and angle by `objects_3d/transition.py`'s `_build_model`/`build`. That code is the most fragile in the whole area and needs a careful read before it is touched.

### 4c. Splitting a bundle (context menu)

- **DECIDED (user, 2026-09-26):** a context menu option on a bundle splits it into 2 bundles, so that a transition can be added in the middle of the bundle. The user then places the transition at one of the two new ends (section 4), makes that one connection there, and connects the other bundle to a remaining free branch by drag and drop.
- **PROPOSED** -- The split happens where the bundle was right-clicked (the closest point on its path, as "Add Handle" already finds it). The two new bundles have the same cover part and diameter; the waypoints/layouts before the split point stay with the first, those after go to the second; each keeps the parts of the path it owns. The split point becomes the first bundle's stop and the second bundle's start; until a transition is placed there they are two bundles that meet at a point, both with a free end. They are NOT merged back: bundles only ever join through transitions.
- **PROPOSED** -- In the peg-board view the bundle is split at the SAME distance along the path (arc length from the start) as in 3D, so both halves keep identical lengths in both views (the length rule, section 6).
- **OPEN** -- Does the "Split" menu action go straight into the transition placement flow at the split point (choose which of the two ends gets it), or does it just split and leave the user to place the transition? Suggestion: split only, then the user places a transition on either end as usual.
- **OPEN** -- Splitting a bundle that already has wires in it changes every routed wire's path; deferred until wire routing exists (suggestion: the menu item is disabled for a bundle that has wires, until then).
- Note: `handlers/bundle_topology.merge_bundles` (two bundles touching end to end become one) has no callers and belongs to the old model; it is obsolete under these rules and to be removed.

## 5. Attaching bundles to transitions

- **DECIDED** (from the routing rules) -- A bundle end attaches to a transition branch; a bundle can have 0, 1 or 2 branches attached (one per end).
- **PROPOSED** -- Attaching = the bundle's start/stop point and the branch's position point are the same row (in 3D and, separately, in peg-board). That is how it works in the storage design: the bundle's own path ends on the branch position, and the branch owns the position.
- **DECIDED** -- Attaching must not create a loop (see the NO LOOPS rule in section 6).
- **DECIDED HARD RULE (user, 2026-09-26): a bundle cannot have both of its ends connected to the same transition.** (The smallest possible loop; it is already excluded by the no-loops rule, but it is coded as its own explicit check with its own refusal message, because it is the case a user is most likely to try: dragging the second end of a bundle onto another branch of the transition its first end is already on.)
- **PROPOSED** -- Only a FREE branch and a FREE bundle end can attach. Attaching sets the bundle's sibling link (`Bundle.set_sibling`) and the transition's (`Transition.add_bundle(bundle, end, branch_id)`); both are in-memory and rebuilt on load by `_reconcile_bundle_sibling_graph`.
- **PROPOSED** -- Helpers needed by placement and later by wire routing: "free ends of a bundle" and "free branches of a transition".
- The existing `PJTBundle.start_layout`/`stop_layout` (a layout marking an end) and the sibling refs both exist today; which one is the source of truth for "free" needs to be settled while writing the helpers.

## 6. How the views react to each other

**DECIDED (user, 2026-09-26) -- the length rule.** When a bundle is placed in the 3D view a bundle MUST also be created in the peg-board view. The key rule: the bundle's length must ALWAYS be identical in the peg-board view and the 3D view. A bundle can never be made longer or shorter in the peg-board view, so moving it there means it has to move within the boundaries of the length the bundle has in the 3D view.

**DECIDED (user, 2026-09-26) -- what "length" and "slack" mean:**
- **Total length** = the length of the bundle from its start position to its stop position, calculated by adding up the distance traveled between each waypoint and the ends (start to first waypoint, each waypoint to the next, last waypoint to stop). This is the polyline length, the same thing `PJTBundle.length_mm` computes.
- **Slack is ONE mechanism** (not several options): the chain behaves like a rope. Dragging a waypoint or an end PULLS the rest of the chain like a rope, as long as slack is available. When an end is moved CLOSER to the start (or otherwise needs slack that is not there), slack is INDUCED: waypoints are ADDED as needed in order to slack the bundle so the total stays identical.
- **A move is REFUSED if there is not enough slack available** (i.e. it would need the distance the bundle spans to exceed its length).
- Same rule for an attached bundle: with both ends on branches at fixed peg-board positions, a shorter distance is absorbed by added waypoints, a longer one is refused.

**DECIDED (user, 2026-09-26) -- the anchor model for peg-board editing** (this is the way to think about it):
- When a bundle is placed, its two ENDS become the ANCHOR points. If one end is clicked and dragged, the OTHER end does not move; the waypoints between the two move so the bundle keeps its proper length. If waypoints are needed to do that they are ADDED, and if waypoints can be removed they are REMOVED.
- **Induced slack shape:** one bowed waypoint absorbs slack but its height is capped at a configurable fraction of the section length; beyond that, another waypoint is added (accepted).
- **The user can move a waypoint**, and doing so PULLS other waypoints along with it, so long as there is slack in the bundle. If there is no pullable slack, the move of a waypoint is NOT allowed.
- **Waypoints can be removed when two bundle sections end up making a straight section** (collinear), which is how the added slack waypoints go away again once the bundle is pulled straight.
- **A length change in the 3D view must be realized in the peg-board view.** The peg-board bundle is always brought back to the same total length as the 3D bundle. (Peg-board edits never change the length, so nothing flows the other way.)
- **Which end moves (user, 2026-09-26):** a bundle has a start and a stop end and only ONE of them moves in an edit. If the bundle has to become shorter (or longer), whichever end is being clicked and pulled in the 3D view is the SAME end that moves in the peg-board view, with the other end kept as the anchor. So there is no "peg-board cannot follow" problem (this replaces the refusal I suggested).
- **If the end that has to move is attached to a transition (user, 2026-09-26): the transition moves to accommodate, and any bundles attached to the transition's OTHER branches are also pulled along with it.**
- **The cascade (user, 2026-09-26):** when a bundle is made shorter in the 3D view, that change must be realized in the peg-board view, and if there are several transitions and multiple bundles attached DOWNSTREAM of the change, the change cascades to all of the positions downstream. EVERYTHING is pulled if slack is not available. In other words the rope rule applies all the way down: each bundle first uses its own slack (its waypoints pull straighter); only when it has none does the pull continue through the transition at its far end (the transition moves; the bundles on the transition's other branches are pulled along, each using its slack first, and so on).
- **Downstream (user, 2026-09-26, confirmed):** everything connected beyond the moved end, on the side away from the anchor end of the bundle that was edited. The anchor side never moves.
- **Transitions ROTATE when pulled (user, 2026-09-26; the user wants the real-life behavior and left the cost decision to me):** the transition rotates so the branch the pulled bundle is connected to moves in the pull direction. Decided: rotate. Cost is negligible: the peg-board is flat, so a transition's pose is just a position and one yaw angle, and the rule below is a few trigonometric operations per transition, well within a Cython solver.
  - **Pivot (user correction, 2026-09-26): the transition's rotation is done using the BRANCH POINT as the origin, NOT the transition's centre.** (My first version rotated about the centre and was wrong.)
  - **Rule (confirmed by the user 2026-09-26: "the body would end up trailing the branch when it is being pulled; that is what would happen in the real world"):** the branch the pull ARRIVES through is the handle (each transition has exactly one arrival branch, because pulls only travel downstream, so there is never a conflict). With `B0` the handle branch's old position and `T` the position the pull moves it to, the pull direction is `d = unit(T - B0)`. The whole transition is first translated so the handle branch sits exactly on `T`; it is then rotated about `T` (the branch point as the origin) so the rest of the transition trails behind the branch, i.e. the direction from the branch to the transition's centre points opposite to `d`. The handle branch's position is therefore exactly `T` and never disturbed by the rotation. Every other branch moves rigidly with the transition (`T + R(phi) * (old_position - B0)`), and the bundles attached to them are then pulled in turn, each using its own slack first. The pure-translation alternative is dropped.
  - Rotation applies to the peg-board pose only (`angle_pegboard`); the 3D pose has its own independent angle.
- **NO LOOPS (user, 2026-09-26):** the skeleton must stay a tree. Attaching a bundle end to a transition branch is REFUSED if it would connect two parts of the skeleton that are already connected (i.e. it would close a ring of bundles and transitions). So the cascade can never run into a loop, and the solver needs no cycle handling.
- **Scope for now (user, 2026-09-26):** get bundle movement nailed down first. What happens to wires and housings when a bundle/transition moves is dealt with later, when wires are added to bundles.

Consequences worked out from that rule (my reading; **PROPOSED** unless marked):
- "Length" can only mean the TOTAL path length (start, through every waypoint, to stop), because waypoint counts and positions are independent per view. The peg-board total must equal `PJTBundle.length_mm` computed from the 3D path (the existing length property; the 3D path is the source of truth).
- The earlier suggestion to seed the peg-board copy by projecting the 3D points onto the floor (x, 0, z) is NOT good enough for bundles: projecting flattens vertical runs and makes the peg-board bundle SHORTER. Seeding must preserve the total length. Suggested: unfold the 3D path -- start at the projected start point (or, if the start is attached to a branch, at that branch's peg-board position), then lay each 3D section out in the peg-board plane with its own 3D length and its projected direction (a vertical section gets a default direction).
- The existing peg-board code is weaker than this rule: `objects_pegboard/chain_edges.py` splits the real `length_mm` across the chain's edges in proportion to their current 2D distances and only CLAMPS a drag so a section is never stretched past its share; the chain may still be shorter than the real length. The new rule means it may not be shorter either.
- A mechanism for absorbing the slack already exists for wires: `handlers/wire_slack.py` bows a single waypoint into a wire's path so its peg-board length reaches the 3D length (`_add_waypoint_pegboard`/`Line.bow_midpoint`). It is untested, and is the natural candidate for bundles whose two ends are pinned (e.g. both attached to transition branches whose peg-board positions are fixed).
- Moving a whole bundle rigidly in the peg-board view always keeps its length. Moving a single waypoint or an end changes the chord and so must be constrained or compensated -- see the open questions.

## 6b. The peg-board rope-pull solver: written in Cython

**DECIDED (user, 2026-09-26):** the code that keeps a bundle's peg-board length identical to its 3D length (rope pull, induced slack, waypoint add/remove, refusal) will be written in Cython so it can be compiled for maximum calculation speed -- it runs on every mouse move of a drag.

Conventions to follow (all from MEMORY.md, "Cython extensions (.pyx)" and the `astar`/`culling` precedents):
- A `.pyx` with the `# cython:` directive header and a tracked `.pyi` stub beside it; hot loops in `.pyx` with C arrays / `nogil`, not compiled `.py`. The binary (`*.pyd`) and generated C are gitignored.

- **Slack scope, confirmed by the user: whole-chain redistribution, not local-zone-only.** Every interior waypoint, anywhere in the chain, is free to move on any drag -- not just the ones nearest whatever was grabbed. Consequence: the solver is STATELESS -- it takes only the two anchor positions (or an anchor and the drag target, for an anchor drag), the drag target, and the required total length, and recomputes every interior waypoint from scratch on every call. It does not read the chain's previous waypoints at all; reconciling the new flat point list against existing DB rows (add/remove/reposition) is entirely the caller's job, not the solver's.
- **Reference skeleton:** dragging an anchor gives a 2-point skeleton `[fixed_anchor, target]`; dragging an interior waypoint gives a 3-point skeleton `[start, target, stop]` (both real anchors stay fixed, the dragged waypoint is pinned as a third fixed point). The skeleton's own straight-line length can never exceed the required total -- if it does, refuse outright.
- **Slack-to-segment split:** proportional by each skeleton segment's own straight length (not a fixed 50/50, not reusing the old `chain_edges.py` per-edge budget mechanism -- this is a new, independent split specific to this solver).
- **One segment's own bow shape (closed form):** `count` independent diamond-shaped bumps side by side, each with half-base `straight / (2 * count)` and apex height `h`, separated by a shared height-0 corner between bumps. `h(count) = sqrt(target**2 - straight**2) / (2 * count)` is exact and strictly decreasing in `count`, so the smallest `count` keeping `h <= height_cap` is `ceil(excess / (2 * height_cap))` -- this is what "add a waypoint once the height cap is exceeded" resolves to concretely, and why bows disappear smoothly as the needed excess shrinks to zero. `height_cap` is `height_cap_fraction * straight` floored at a `min_height_mm` constant, so two near-coincident fixed points don't force an unbounded bow count. `count == 1` reduces to exactly `geometry.line.Line.bow_midpoint`'s own single-bow construction.
- Verified (`scripts` per MEMORY.md's own Cython-verification convention, not committed -- ad hoc, rerun before the Cython port): total length matches the required length after every accepted move; a non-dragged anchor never moves; an impossible drag is refused with no points to apply; bow count shrinks to 0 as needed slack shrinks to 0.

## 6c. Rope-pull cascade: transition rotation and the Rope Pull toggle (built 2026-10-05, NOT yet run in the GUI)

- **Rotation of a pulled transition.** When the cascade pulls a Transition through one of its branches (the "handle"), the whole pose changes, not just the position: its centre and every branch are rotated about the handle branch's point, so the body trails the pulled branch (`handlers/rope_pull_handler.py` `_rotated_and_translated`, angle `phi` chosen so the centre ends up opposite the pull direction). The transition's peg-board yaw is composed by the same `phi` (`angle += Angle.from_axis_angle(Y, phi)`), so the body and branch tips are re-derived from the new pose.
- **Write order (`_commit_points`).** Yaw first, then points. The transition's angle callback rebuilds its branch tips from whatever position/angle it holds at that moment, so the point writes must run last.
- **Cached instances, not just rows.** Every moved point is updated through its cached `Point` (`PJTPointPegboard.point`) with `point += Point(dx, 0, dz)`, and the transition's yaw through its cached `Angle` (`transition.angle_pegboard`) with `+=`. Plain assignment (`point.x = x`) does not fire the bound callbacks that write the row and refresh live views, so it leaves the cached instances and the DB disagreeing. Rule: move cached geometry by delta with `+=`, never by assignment.
- **Caveat.** `Angle.__iadd__` composes by adding Euler angles, which is exact only when the angle is pure yaw. Peg-board angles are edited on the Y axis only (`AnglePegboardControl`, `axes='y'`), so this holds for normal data; a stored non-yaw peg-board angle would rotate slightly wrong. Not verified against the real rows.
- **Rope Pull toggle (rewritten 2026-10-05 after live testing).** `Config.editor_pegboard.rope_pull.enabled` (default on), a "Rope Pull" checkbox on the Peg Board toolbar. Read on every drag and on every 3D length change, so no restart is needed. The toggle controls whether moves may PULL other objects; the slack take-up of a chain always runs.
  - **On:** a drag pulls the rest of the chain and cascades downstream (section 6, `resolve_rigid_move` / `_evaluate_points` with `cascade=True`).
  - **Off:** no other object is pulled and no far end moves (`cascade=False`). The dragged object is clamped instead, so the chain it sits on keeps its 3D length. For a single start/stop anchor the mouse target is projected onto the circle of radius equal to the chain's 3D `length_mm`, centred on the chain's other, fixed anchor (`clamp_to_length_from_anchor`). Multi-chain points (e.g. a transition) and interior waypoints fall back to the largest fraction of the drag line every touching chain accepts (`resolve_local_move`).
  - In both modes, if a move brings a chain's start and stop closer together, that chain's own zig-zag slack is re-solved (the take-up), so its peg-board length stays equal to its 3D length.
  - The old per-edge budget clamp (`DragHandlerPegboard._apply_local_clamp`) is no longer used by this handler.
- **Bundle and wire segment drags** have their own handlers and are not affected by the toggle.
- **Still open.** Behaviour of the toggle and of the rotation has not been exercised in the live app; the peg-board angle caveat above has not been checked against stored rows.

## 6d. Zig-zag count and threshold for induced slack (user spec, 2026-10-05; built the same day)

Applies whenever a span needs slack (3D length above its straight start-to-stop distance). Evaluated fresh on every solve, so it runs again whenever the chain's length changes or something attached to it moves.

- **Diameter.** The bundle's effective diameter (`PJTBundle.diameter`), or a wire's conductor OD (`part.od_mm`). Clamped to at least 1 mm (`_MIN_DIAMETER_MM`) so a zero diameter cannot divide by zero.
- **Maximum zig-zags.** `max_count = max(1, floor(S / (zigzag_length_factor * D)))`, where `S` is the span's straight start-to-stop length and `zigzag_length_factor` defaults to 3 (`Config.editor_pegboard.rope_pull.zigzag_length_factor`, placeholder, untuned).
- **Threshold height.** `threshold = threshold_factor * D`, where `threshold_factor` defaults to 1 (`Config.editor_pegboard.rope_pull.threshold_factor`, placeholder, untuned). This is the height every existing zig-zag must reach before another is created. It is a threshold, not a minimum amplitude.
- **Count.** `count = clamp(floor(excess / (2 * threshold)), 1, max_count)`, with `excess = sqrt(T**2 - S**2)` and `T` the span's required length. A zig-zag is only added once every existing one could already stand at least `threshold` tall.
- **Height.** `height = excess / (2 * count)`, the exact height for `count` equal bows (see the closed form in `rope_pull_py.py`).
- **Gate once the cap is reached.** When `count == max_count`, the amplitude keeps growing and shrinking with the slack. When the slack falls back below a threshold, `count` drops by one, so slack comes out of one zig-zag at a time. The floor makes each change a single step.
- **Replaces** the previous `height_cap_fraction` / `min_height_mm` / `max_zigzags_per_mm` rules (removed from the config, reference, Cython port, stub, dispatcher and handler). The earlier rule treated the height as a ceiling; this one treats it as a threshold.
- **No amplitude cap.** The amplitude is not limited. An amplitude cap combined with the count cap would make some slack unstorable, so if one is added the solver must refuse the move rather than crash (see the discussion of 2026-10-05).
- **Verified (reference only so far).** The pure-Python solver on 2000 random chains: every result totals the required length, and with D = 30 and S = 300 the bow count stays within 3 and changes by one bow per step. The compiled `rope_pull.pyd` could not be rebuilt in the same session because the running app holds it open, so the compiled-vs-reference comparison is still outstanding.

## 12. Wire-into-skeleton drag-and-drop (decided 2026-10-03)

How dragging an existing wire onto the skeleton actually works at the mouse-interaction level -- the UI half of `BUNDLE_DESIGN.md` 2.7/`wire_routing_handler.py`'s own chain-walk engine (built 2026-10-03, see that module). Splices are NOT covered here yet -- user, 2026-10-03: "we will get to how to handle splices a little bit later." Until then a route that would need to end at a splice simply has no exit to pick and is left incomplete (refused), not built around.

**Eligibility precondition (user, 2026-10-03), sharpening 2.7's own "a section between 2 waypoints" rule:** a wire can only be dragged into a bundle/transition if it has at least 2 of its OWN waypoints, and the dragged section is the stretch BETWEEN two of those waypoints -- never a section touching the wire's own start or stop. (In `_segment_index` terms, against `[start] + interior + [stop]`: only `1 <= section_idx <= len(interior) - 1` is a legal grab, requiring `len(interior) >= 2`.) A wire with 0 or 1 interior waypoints, or a grab on the first/last segment, cannot start a route at all.

**The gesture is the EXISTING interior-waypoint-pair drag, not a new one (user, 2026-10-03): "when the wire section is dragged the wire should move as usual."** The wire's grabbed waypoint pair moves with the cursor exactly like an ordinary bend-drag, unchanged. What's new is purely what happens on drop: if the cursor is over an eligible bundle free end or free branch when released, the wire routes into the skeleton instead of just staying bent there. A drop anywhere else is an ordinary bend, exactly as today -- same gesture, classified by what's under the cursor at release, not two different gestures to tell apart up front.

**Bundle traversal (user, 2026-10-03):** dropping onto a bundle walks the ENTIRE bundle to its far end automatically (matches the engine's own behavior). If that far end sits on a transition, the interaction becomes click-based from there: **"the user would then need to click on the branch the wire should exit the transition out of."** Entering directly onto a transition's own free branch (no bundle) works the same way, then also continues via a click. So the overall shape is: one drag commits the FIRST hop (into a bundle, walked to its far end, or directly onto a free branch); every transition reached after that -- however many in a row -- is resolved by a separate click on the exit branch, not by continuing to hold the drag through it. **"If there is a bundle attached to that branch then the wire should go to the end of that bundle. This process will continue until the wire exits either from a transition branch that doesn't have a bundle or from a bundle end not attached to a transition."** This is exactly `wire_routing_handler.route_wire`'s own `ContinueBranch`-chasing loop; the UI session accumulates one hop per click and only calls `route_wire` once, when a genuinely free end is finally reached.

**Fit-checking is mandatory at every step (user, 2026-10-03): "any time a wire is dragged and any time there is a transition branch selection that needs to be made a check needs to be made to see if the wire will fit... only branches/bundles where the wire can fit should allow the wire to be added."** Two-tier visual, not a single highlight (user, clarifying 2026-10-03): the moment the drag starts (or the moment a transition is reached needing a branch pick), EVERY eligible bundle/branch is recolored immediately so the whole set of valid targets is visible at a glance -- not just whatever the cursor currently happens to be over. Hovering one of those already-recolored targets then brightens/changes it further to mean "drop here." A target that doesn't fit is never recolored at all (no "doesn't fit" color needed for this interaction, unlike the bundle/transition PLACEMENT flows' own red/orange no-fit highlight -- it's simply excluded from the eligible set).

**Fit formula (user, 2026-10-03): "the minimum of the max bundle diameter and the max branch diameter is what needs to be used when checking to see if a wire will fit. This check also needs to be done at the opposite end of the bundle if a transition is attached because that transition could restrict the diameter to be smaller and the wire might not be able to go through to the other transition."** For a candidate bundle: the capacity ceiling is `bundle.part.max_dia`, further narrowed to `min(..., branch.part.max_dia)` for EVERY transition branch attached to EITHER of the bundle's own two ends (not just the end being entered) -- a bundle whose far end is already plugged into a tight transition can refuse a wire even though the near end being dropped onto has plenty of room. For a candidate bare branch (no bundle attached), the ceiling is just that branch's own `part.max_dia`. Reads as: `effective_diameter(bundle_or_branch) + new_wire`'s own contribution must stay within that ceiling -- the same wire-driven-diameter formula `handlers/bundle_diameter.py` already computes (concentric layer diameter if twisted, else the `sqrt(sum(od**2))` unorganized-pack estimate) is reused here, now compared against a MAX ceiling instead of that module's own MIN floor. (This reading -- hypothetical packed diameter vs. ceiling, not a bare single-wire-OD vs. ceiling comparison -- is Claude's own inference from how `bundle_diameter.py` already frames "diameter a bundle needs," not a literal quote from the user; flag for correction if wrong.)

**Still open / not decided here:** exactly how "the wire's own diameter" is sourced for an UNROUTED wire with no bundle membership yet (presumably `wire.part.od_mm`, matching `bundle_diameter.py`'s own per-wire OD read); whether the two-tier highlight uses new dedicated materials/config colors or reuses `transition_handler._BRANCH_FIT`/`_HOVER_HIGHLIGHT` as-is; how a BUNDLE (as opposed to a branch, which already has `highlight_branch`) gets recolored, since no existing highlight-override mechanism for a whole bundle object was confirmed as of this entry -- see the implementing code/commit for however these were actually resolved.

- 2026-10-05 (mid-drag slack, offline store): While a drag runs, a chain that needs less slack gives up its surplus waypoints one at a time from the anchor end (the end not being moved). Each goes to index 0 of an in-memory per-chain store (`rope_pull/offline_store.py`) and its layout is hidden. Path rows and point rows are untouched during the drag, so no `idx` changes and nothing is deleted. The store is the only thing that changes mid-drag, and only the drag code touches it. When the chain needs slack back, the store's index 0 comes back first. The peg-board strand skips out-of-service waypoints (`_bind_waypoints` in `objects_pegboard/bundle.py` and `wire.py`). On release the store is emptied, layouts are made visible again, and the normal reconcile reuses or deletes rows and rewrites `idx`. Not yet run in the live app; the layout visibility setter (`is_visible_pegboard`) is assumed to be a real setter on the peg-board layout rows.
- 2026-10-05 (no DB write for hide/restore): Mid-drag visibility changes set only the peg-board object's own cached value (`BasePegboard.set_visible_cache`, which sets `_is_visible`) and never write `is_visible_pegboard`. The persisted value is never changed during a drag, so release only has to restore the cache. The property setter (which writes the database) is no longer used by the drag path.
- 2026-10-05 (drag overlay, no database writes mid-drag): Each chain a peg-board drag touches keeps an in-memory overlay of its in-service waypoints (`rope_pull/offline_store.py`). Entries are database-backed points, or new in-memory points made with `PseudoPJTBundleLayout` / `PseudoPJTWireLayout` (never written until release). When the solver wants more waypoints, the store's most recent entries come back first, and new in-memory points are created only when the store is empty. The peg-board strand draws from the overlay (`overlay_points`). On release `_commit_overlay` inserts rows for new points, sets the route in overlay order, creates their layouts, and deletes layouts no longer in the route. Chains with no overlay (e.g. 3D realisation) keep the old reconcile. Not yet run in the live app.
