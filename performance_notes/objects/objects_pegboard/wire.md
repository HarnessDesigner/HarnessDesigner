# harness_designer/objects/objects_pegboard/wire.py

## Line 499-... (`Wire.render`) — same structure and costs as the 3D wire
The pegboard wire renders each sub-segment through the full `BaseVar` pipeline, and it rebuilds the per-segment conductor `Point` every frame when a crimp segment is drawn. The stripe pass and its per-frame helix lookup have the same shape as the schematic wire. The shared costs and fixes are written up in `performance_notes/objects/objects_3d/wire.md` and `objects_schematic/wire.md`; they apply here unchanged.

## Line 288-340 (`_update_angle`, `_recalculate_geometry`, `_update_position`) — recalculation on every drag move
Same pattern as the 3D wire: every endpoint or waypoint move recalculates length, bounds, and the stripe capacity. See `objects_3d/wire.md`.

**Fixed for the rope-pull drag path specifically (2026-10-16).** `handlers.rope_pull_handler._apply_mid_drag` moves several of this wire's own interior waypoints one at a time (`_place_active`'s loop), and each one left bound to `_update_position` paid for its own full recalculation -- confirmed live as the dominant per-point cost of a peg-board drag. Added `unregister_geometry_updates()` (unbind `_update_position` from every current waypoint, no rebind) and `reregister_geometry_updates()` (rebind to that exact same set, no re-derivation, no `WireSlackHandler.register_pegboard` rebind -- only valid when the caller already knows the waypoint SET itself didn't change). `_apply_mid_drag` unregisters before its move loop, then picks one of the two afterward in a `finally`: the full `refresh_waypoints()` when something actually changed, the cheap `reregister_geometry_updates()` on a true no-op. One recalculation now replaces what used to be one per waypoint moved, and is skipped outright on a no-op -- cheaply, with no DB/offline-store re-derivation either (an earlier version of this fix gated only the recalculation behind a flag but still re-derived+rebound unconditionally, which became the new dominant cost; see `handlers/rope_pull_handler.md`'s own note on that). Every other `refresh_waypoints()` call site in the codebase is untouched by any of this.

**Second, parallel over-binding found in `_bind_waypoints()` itself (2026-10-16, same session), confirmed live: `Wire._update_position` fired exactly 3 times per housing-move frame both before AND after the `WireSlackHandler` fix below.** `_bind_waypoints()` was binding `_update_position` to EVERY interior waypoint, including every terminal/cavity structural-stub point individually (same root cause as `handlers.wire_slack_handler.WireSlackHandler.register_pegboard`'s identical bug -- see that method's own note) -- `PJTHousing._update_position_pegboard` always moves a seated terminal's own attach point, its own stub, and its cavity's stub by the exact same delta, so binding to all of them means moving the housing fires this wire's own full `_recalculate_geometry()`/GL-stripe rebuild once per stub point instead of once per housing move. Fixed by computing `leading`/`trailing` via `rope_pull_handler.stub_boundary_for_chain` (a lazy, cycle-avoiding import inside `_bind_waypoints()` itself, same reason `wire_topology` is already imported lazily there) and binding only the slice from the innermost leading stub through the innermost trailing stub -- `self._waypoint_points` itself shrinks to this reduced set, which is safe because that attribute is used ONLY for bind/unbind bookkeeping (`_bind_waypoints`/`unregister_geometry_updates`/`reregister_geometry_updates`), never for rendering (`_segments()`/`_live_waypoint_ids()` read the DB/overlay directly, independent of this list) -- confirmed by checking every use site before making this change.
