# performance_notes/database

Covers `harness_designer/database/`. Rewritten 2026-11-13 after the project tables moved to an in-memory table store and the global tables got a row cache. Numbers below were measured on a copy of the real 395 MB `harness_designer.db` (copied to a scratch folder, never the live file) and with throwaway scripts; the app itself was not run.

## How data reaches the app now
- **Project tables (`pjt_*`) are cached in memory.** `PJTTableBase.load_cache` (`project_db/pjt_bases.py` line 505) reads every row of the project's id range once into a `TableData` (`project_db/table_data.py`): one dict per row. Reads (`__getitem__`, `__iter__`, `__contains__`, `select`) never touch SQL. A `select` that names a column is answered from a lazily built per-column index; `OR` selects and short tables scan. Writes outside a gesture are `UPDATE` + `commit` + a mirror into the cache; inside a gesture (`PJTTables.begin_gesture`, drags and rotations) they only change the cache and land in one transaction on `end_gesture` (`WRITE_DESIGN.md` 4.12). See [project_db/table_data.md](project_db/table_data.md) and [project_db/pjt_bases.md](project_db/pjt_bases.md).
- **Global tables (the catalog) are cached per live wrapper.** `EntryBase.__init__` calls `TableBase._cache_row`, which runs one `SELECT <all columns> WHERE id=?` for that row and keeps the dict until the wrapper is garbage collected (`_evict_row`). Every `select('col', id=...)` for a cached row is a dict lookup. `__getitem__` and `__contains__` on a global table still query SQL, behind the singleton short-circuit (`item in EntryClass or item in self`). See [global_db/bases.md](global_db/bases.md).
- **The property getters in the per-class notes no longer mean one query each.** A getter that issues `self._table.select('col', id=self._db_id)[0][0]` is a dict lookup on both sides; the `_stored_*` / `DefaultStoredValue` guard saves only the call overhead.

## Highest-value findings
1. **Memory: the project table store keeps a dict per row.** A 20-column row measured 601 bytes for the dict and the order bookkeeping, plus the value objects (a float is 24 bytes, a 16-byte id 49 bytes, so about 25-50 bytes per cell), which makes roughly 1.1-1.6 KB per 20-column row, or about 11-16 MB per 10,000 rows; 50,000 rows is 30 MB of dicts alone. `WRITE_DESIGN.md` open item 7h notes the size on a large project has not been measured. Storing rows as tuples with one shared field-name -> position map would shrink the container part to about a third (a 20-item tuple is about 216 bytes against 601; the value objects are unchanged), but every cell read becomes a position lookup and `TableData` is written around dict rows; only worth doing if a real large project shows memory pressure. The cache is a deliberate speed-for-memory trade (the project is open for hours, and the alternative was one SQL round trip per property read).
2. **`OR` selects scan the whole table.** `TableData._candidates` returns `list(rows.values())` for `OR=True`, so each call costs about 0.4 us per row (measured 20.6 ms at 50,000 rows). Call sites: the `is_referenced` checks in `pjt_point3d.py` (14 selects), `pjt_point2d.py` (4) and `pjt_point_pegboard.py` (9), run on every point delete; and `handlers/rope_pull_handler.py` (`_lead_pieces`, `_is_owned_end`, `_node_for_point`), which run inside drag frames. An `OR` over indexed columns can be answered as a union of the per-column index hits (the machinery is already there). Memory price: one index per column asked about (a dict value -> set of ids, roughly 100-150 bytes per row per column; for a 500-wire table about 100 KB), so it is cheap for the small tables rope pull touches and for the points tables is a few MB at most.
3. **Raw SQL per drag frame.** `PJTHousing._find_child_points` and `_find_child_points_pegboard` (`pjt_housing.py` lines 1818 and 1854) run `SELECT id FROM pjt_points3d WHERE parent_point_id IN (...)` through the connector on every housing move and rotate frame (called from `_update_position3d`, `_update_angle3d`, `_update_position_pegboard`, `_update_angle_pegboard`). It bypasses the cache, scans the table in the database (no index on `parent_point_id`) and sends the writes of the same gesture nothing, because the gesture's changes are still only in the cache. One cached-index lookup per canonical id would replace it. `WRITE_DESIGN.md` 7a lists it as the known residual read cost.
4. **Filtered part search on the big catalog tables is a full table scan.** On the real database: `SELECT id FROM housings WHERE family_id=?` takes 35 ms (81,093 rows) and 0.1 ms after `CREATE INDEX ... ON housings(family_id)`; the search dialog's three-join query takes 69 ms with one filter and 276 ms unfiltered. The catalog tables have only the primary key and the `UNIQUE` `part_number`/`name` indexes; the FK filter columns (`mfg_id`, `family_id`, `series_id`, `gender_id`, `direction_id`, ...) have none, except `wire_conductors.wire_id` and `deratings.*_id`, which do. Cost of adding them: disk (an index on 81,000 rows is about 3 MB; a dozen on housings is roughly 30-40 MB on a 395 MB file) and some build/seed time, with almost no resident memory (SQLite caches only the pages it touches). It must be added in both repos (the `harness_designer_database` builder builds the downloaded file) and applied to databases already downloaded (`_update_table_in_db` only adds missing columns). Do it for the columns the search dialog really filters on, not for all.
5. **Per-wrapper row loads.** Each new global wrapper costs one `SELECT` of about 17-20 us (measured: 200 single-row selects 3.4 ms; one `IN (200)` query 1.7 ms). Building wrappers for thousands of search results is thousands of queries; a batched preload (`TableBase._cache_rows(ids)` with `IN (...)`) would halve that. Full-table `SELECT *` on housings is 553 ms (ids only: 31 ms), so the per-row design is right for big tables and the batched preload is the only improvement worth making.
6. **Unused module:** `database/config_db.py` is imported by nothing (`dep_trace --imported-by` finds no importer); `config.py` has its own copies of the same classes. See [config_db.md](config_db.md).

## Other patterns
- **Seeding is per row.** The `create_database/*.py` modules insert the built-in catalogue row by row (each `add_*` calls `get_*_id` lookups, each its own `SELECT`), but only when the table is empty (`add_records` checks first), so the cost is paid once on a first build. Not worth changing.
- **Row ids** are generated client-side per row (`id_generator`): on SQLite a lock plus a clock read; on MySQL a stored function. Negligible except in bulk seeding.
- **Metaclass singletons:** `_EntrySingleton` and `_PJTEntrySingleton` keep a weak `_instances` registry under a lock; every wrapper construction and lookup takes that lock.
- **Commits:** the SQLite connection is in WAL mode with `synchronous=NORMAL` (`sqlite_connector/connector.py` `_enable_wal`), so a commit costs about 0.015 ms; the cost model is statements and Python row building, not commits (`WRITE_DESIGN.md` section 2). Outside gestures every `update` is still its own commit.

## Known issues found during this review (not fixed here)
- `db_connectors/mysql_connector/settings_dialog.py`: `getattr(Config, 'kerberos_auth_mode', 'SSPI')` reads a name that `config.py` defines inside the nested `mysql` class, so the lookup probably always returns `'SSPI'`. A functional question, not a performance one.
- `project_db/pjt_bases.py` `PJTTables.tables` (line 1359) builds its list by reflecting over `dir(self)` on every access. Used by the load path, so it is not hot.
