# harness_designer/handlers/rope_pull_handler.py

## Line 838-929 (`resolve_rigid_move`) — up to 34 full evaluations per mouse move
This is the largest cost in the handlers folder, and it runs on every mouse move of a peg-board rigid drag. When the full move does not fit (line 906-909), the function does a binary search over the move fraction. It evaluates the endpoints (line 913) and then `iterations` midpoints (line 915-924). `iterations` defaults to 32 (line 842), so a move that does not fit costs up to 34 evaluations.

Each evaluation calls `_evaluate_points` (line 624), which calls `_chains_for_point` (line 314) for every point it moves (line 749).

**Fixed (2026-10-16):** `resolve_rigid_move`, `resolve_local_move`, and `_resolve_pinned_move` each build one `chain_cache` dict before their sequence of `_evaluate_points` calls and pass it to every one of them — see the next section.

## Line 314-357 (`_chains_for_point`) — full scan of the bundles and wires tables per point
For each point, the function iterates over every row of `pjt_bundles_table` (line 343) and every row of `pjt_wires_table` (line 350), and calls `_drag_end_for` on each. The cost is (bundles + wires) per moved point, per evaluation. With 34 evaluations per move, that is 34 × points × (bundles + wires) row visits per mouse move.

The move fraction does not change which chains touch a point, so the chain list could be built once per drag (per moved point) and reused across the whole search. That is the single change with the largest payoff in this folder.

**Fixed (2026-10-16):** the anchor-side fallback (a point that is neither a bundle- nor wire-path interior waypoint) now goes through `_anchor_index` — one pass building a `point_id -> chains` dict — instead of scanning every bundle/wire per lookup. `_chains_for_point` takes an optional `cache` dict; `_evaluate_points` takes a matching `chain_cache` and defaults it to a fresh local dict when not given, so even one call's own cascade (`pull_node`'s stale-chain scan plus the main worklist loop) shares a single index build. `resolve_rigid_move`/`resolve_local_move`/`_resolve_pinned_move` each build one `chain_cache` up front and pass it to every `_evaluate_points` call in their binary search — safe because `_evaluate_points` is a pure read-only solve (no DB writes happen until the winning candidate's `_commit_points` call, after the search ends), so the bundle/wire → anchor-point mapping cannot change mid-search. This turns the per-mouse-move cost from O(evaluations × points × (bundles + wires)) into one O(bundles + wires) index build per mouse move plus O(1) lookups thereafter. Verified against the old brute-force scan (including the degenerate start==stop case) with a standalone comparison script; no project test suite covers this module. The now-unused `_drag_end_for` was deleted.

**Root cause found (captured trace, 2026-10-16), dragging a housing with a wire attached.** The chain_cache fix was real and worked -- every lookup/geometry helper in the captured trace is sub-millisecond. The actual cost has two parts:

1. **The wire's full reconcile ran 4 times per mouse-move frame, not once.** `Generic.__call__` calls `resolve_rigid_move` once (the legitimate cascade). Right after, `objpegboard.drag()` applies the move to the housing's own DB point, and `PJTHousing._update_position_pegboard` carries that onto each wire-bearing terminal by moving three separate points (the terminal's attach point, its own wire-stub point, the cavity's wire-stub point) one at a time. `WireSlackHandler` (`handlers/wire_slack_handler.py`) binds its reconcile callback to every point on a wire, including those stub points, and its reentrancy guard (`_reconciling_any`/`is_committing()`) only blocks *nested* re-entry, not these three *sequential* calls -- so `realize_length_change` reran the same wire's full solve+commit three more times, each ~140-380ms, on top of `resolve_rigid_move`'s own pass.

2. **Each `_move_point` call cost ~14-24ms on its own**, confirmed by reading `objects_pegboard/wire.py`: `Wire._bind_waypoints()` binds `Wire._update_position` to *every* one of the wire's points (start, stop, every interior waypoint), and that callback calls `_recalculate_geometry()` -> `_segments()` (every segment, every point) -> `WireStripe._ensure_stripe_capacity()` (a GL buffer resize/create) -> `_compute_obb()`/`_compute_aabb()`. So moving N waypoints one at a time inside `_place_active`'s loop paid for N full wire-geometry-and-GL-stripe rebuilds, when `_apply_mid_drag` already does one unconditionally via `refresh_waypoints()` at the end of every call.

**Fixed (2026-10-16), part 1:** `_move_point` now no-ops (skips the `+=` and therefore every bound callback) when the target is exactly where the point already is -- exact equality, never a tolerance, so this only ever skips a call that would have been a provable no-op. `_place_active` and `_apply_mid_drag` thread that "did anything actually move" signal through, so `_apply_mid_drag`'s own trailing `refresh_waypoints()` is also skipped on a true no-op (same count, same positions). This collapses each of the 3 redundant `WireSlackHandler`-triggered passes to near-zero cost, since by the time they run the wire is already exactly where `resolve_rigid_move`'s own pass just put it.

**Fixed (2026-10-16), part 2:** `objects_pegboard.wire.Wire` and `objects_pegboard.bundle.Bundle` both gained `unregister_geometry_updates()` (unbind `_update_position` from every current waypoint, no rebind) and `reregister_geometry_updates()` (rebind to that exact same set, no re-derivation, no `WireSlackHandler.register_pegboard` rebind). `_apply_mid_drag` calls `unregister_geometry_updates()` before `_place_active`'s per-point move loop, then in a `finally`: the full `refresh_waypoints()` (re-derive the waypoint set, rebind everything, recalculate, repaint) only when something actually changed (`original_count != len(active) or moved`), else the cheap `reregister_geometry_updates()`. This only suspends the WIRE/BUNDLE's own aggregate-geometry callback specifically -- it does not touch any other callback a waypoint's own marker facade might bind for its own rendering, so there is no risk of a waypoint sphere's own position-sync going stale from this change.

**First version of part 2 regressed this (caught by a second live capture, same session):** an earlier version added a `refresh_waypoints(recalculate: bool = True)` parameter and called it *unconditionally* (gating only `_recalculate_geometry()`/repaint behind the flag), reasoning that the rebind always had to run since `unregister_geometry_updates()` always unbound first. That reintroduced unconditional `_bind_waypoints()`-driven re-derivation and `WireSlackHandler.register_pegboard()`'s own re-derivation+rebind on *every* call, including no-ops -- visible in the capture as `_apply_mid_drag`'s own self-time becoming the dominant cost (947ms self / 53 calls, far more than its decorated children). `reregister_geometry_updates()` replaces that: a true no-op only ever rebinds to the identical, already-known list, no re-derivation and no `WireSlackHandler` involvement at all. The `recalculate` parameter was removed again since nothing calls `refresh_waypoints(recalculate=False)` anymore.

**Part 3 (2026-10-16), found via @debug.logfunc instrumentation added to `objects_pegboard/wire.py`/`bundle.py`/`mixins.py`/`handlers/wire_slack_handler.py`.** Parts 1 and 2 fixed `_apply_mid_drag` completely (its own self-time dropped from 4388ms to 1.95ms in the capture that proved it), but the SAME drag still cost ~2.8s total, now dominated by `Wire._compute_obb`/`_compute_aabb` (228 calls, ~5.2ms each, ~2.4s combined) via `Wire._recalculate_geometry` (114 calls). Root cause, per the user's own diagnosis: `WireSlackHandler.register_pegboard` was binding its reconcile callback to the wire's TRUE start/stop anchor AND every structural stub waypoint individually (up to 3 points per end -- the terminal's own `attach_position_pegboard`, its `wire_position_pegboard` stub, and the seated cavity's own `wire_position_pegboard` stub), when `PJTHousing._update_position_pegboard` always moves all of a seated terminal's points by the exact same delta -- they never move independently. Binding to all of them meant one housing move fired this wire's own full reconcile (and `Wire._update_position`'s own full geometry rebuild, separately, for direct stub-point bindings) up to three times over for the one semantic event. Fixed in `register_pegboard` itself (not in `pjt_housing.py`, which is correctly one-directional already -- housing moves the wire, never the reverse): bind only the INNERMOST point present at each end (the cavity's own stub if seated, else the terminal's own stub, else the wire's own true anchor if that end isn't terminal-attached at all), using the existing `stub_boundary_for_chain` leading/trailing counts (renamed public from `_stub_boundary_for_chain`, previously only used by `_anchors_and_length` for a different reason -- excluding stubs from the solver's own free interior). The free interior waypoints in between are still bound individually, unchanged. Verified the index math (which point is "innermost" for every leading/trailing combination, including the all-stub/no-free-interior edge case) with a standalone test; the live effect (whether `_compute_obb`/`_compute_aabb`'s call count actually drops) still needs a fresh capture to confirm.

**Part 4 (2026-10-16), same root cause, found independently in `Wire._bind_waypoints`'s OWN binding (not `WireSlackHandler`'s).** Confirmed live that part 3 alone didn't move `Wire._update_position`'s own per-frame call count at all -- `_bind_waypoints` binds this wire's OWN `_update_position` (the geometry-rebuild trigger, separate from `WireSlackHandler`'s reconcile trigger) to every structural stub individually too, same bug, same fix: bind only the slice from the innermost leading stub through the innermost trailing stub, via the same `stub_boundary_for_chain` call (lazy-imported inside `_bind_waypoints` to avoid a cycle, same reason `wire_topology` is already lazy-imported there). `self._waypoint_points` itself shrinks to the reduced set -- safe because that attribute is used only for bind/unbind bookkeeping, never rendering (checked every use site first).

**Part 5 (2026-10-17), a raw Python call-stack dump logged from inside `_compute_obb` (`debug.is_capturing()`-gated -- the `debug.logfunc` call tree can't see through `Point.__iadd__`'s own undecorated callback dispatch) found a GENUINE bug, not drag-path redundancy: `Wire._recalculate_geometry`/`Bundle._recalculate_geometry` were calling `_compute_obb()`/`_compute_aabb()` TWICE per invocation, unconditionally, regardless of caller.** `self._scale.z = total_length` (a `Point.z` setter, which unconditionally fires callbacks) already triggers `BaseVar._update_scale` (bound to `self._scale`), which calls both -- and the function's own since-removed trailing calls did it again. Confirmed by the exact 2:1 ratio holding in every capture. This is caller-independent: fixing it once here halved the remaining cost across every path that reaches `_recalculate_geometry` (the housing cascade, `WireSlackHandler`, `_apply_mid_drag`'s own pass) at once, without needing a per-caller fix. Safe to remove because `_compute_obb`/`_compute_aabb` only read `_segment_transforms()`'s own fresh-each-call data, never `self._scale`/`self._angle` (both still unset when the scale assignment fires them). The 3D-view counterparts (`objects_3d.wire.Wire`/`objects_3d.bundle.Bundle`) are documented as mirroring this code and likely have the same bug -- not fixed, out of scope for the peg-board drag this session tested.

**Part 6 (2026-10-17), the user's own proposed fix: a per-chain marker so the LAST point of a batch to move is the only one that triggers a real rebuild, regardless of how many unrelated code paths moved points in that batch.** Parts 3/4 reduced each wire end to one bound point, but that one point can still be moved by THREE different, uncoordinated callers in one housing-drag frame (`PJTHousing._update_position_pegboard`'s own direct cascade, `_commit_points_body`'s `write_points` loop for cascade-pulled anchors, and `_apply_mid_drag`'s own per-waypoint loop) -- each previously paid for its own full rebuild. Replaced `Wire`/`Bundle`'s `unregister_geometry_updates`/`reregister_geometry_updates` (literal unbind/rebind) with `suspend_updates`/`resume_updates` -- initially a ref-counted marker, later simplified to a plain bool (`_update_suspended`) per the user's explicit request, since none of the three call sites actually needed nesting support in practice. While suspended, `_recalculate_geometry` (the gate was moved here from `_update_position` -- see part 7) just sets `_update_pending` instead of recalculating; `resume_updates` clears the flag and recalculates once iff anything was actually pending, or does nothing for a true no-op. Extended to all three call sites: `_apply_mid_drag` (unchanged scope, renamed), `_commit_points_body` (suspends every chain in `entries` plus every chain bound to a `write_points` anchor, for its WHOLE body -- yaw writes, point writes, and the entries loop together), and `PJTHousing._update_position_pegboard` (suspends every chain bound to any of `all_positions`, via a lazy cross-package import to avoid the same cycle `objects_pegboard.wire.Wire._bind_waypoints` already avoids -- confirmed safe by simulating the lazy import after the full app module graph loads). `_place_active`'s own `moved`-tracking return value became dead code once `resume_updates` took over detecting "did anything in this batch actually move," and was removed.

**Part 7 (2026-10-17): the gate moved from `_update_position` into `_recalculate_geometry` itself, per the user's explicit instruction**, so EVERY path that reaches `_recalculate_geometry` honors the suspend flag, not only the one that happens to go through the `_update_position` callback. `_update_position` is now a thin, unconditional call straight into `_recalculate_geometry`.

**Part 8 (2026-10-17): the REAL remaining bug -- `_update_position_pegboard` and `_commit_points_body` were looking up "which chain owns this point" through the peg-board path tables by point id, and that lookup silently found nothing for some points.** A structural stub point (`terminal.wire_position_pegboard`/`cavity.wire_position_pegboard`) can be a per-wire CLONE whose own id never matches what the wire's own path-table entry for that stub is keyed by (see `_structural_stub_ids`'s own docstring: "every terminal/cavity stub past the first wire on that terminal is a clone at the same spot"). Confirmed via a raw call-stack dump logged from inside `Wire._compute_obb` (a temporary diagnostic, since removed along with `debug.is_capturing()` once this was found and fixed): roughly half the `_compute_obb` calls in one capture reached it WITHOUT ever going through `resume_updates()` -- meaning the housing-cascade loop's own suspend call was never applied to that wire in the first place, because the id-based lookup missed it. An attempted fix of gating `_compute_obb`/`_compute_aabb` directly too (in case something was bypassing `_recalculate_geometry` outright) was tested live and made no difference, confirming they are ONLY ever reached through the already-gated `_recalculate_geometry` -- that experimental gate was removed again. The actual fix: replaced the `_chains_for_point`-based `chain_objpegboards_for_point` helper with `chains_bound_to_point(point)`, which inspects *point*'s own already-bound callbacks directly (`point.__callbacks__`, the exact weakref list `CallbackMixin._process_callbacks` itself fires from) and returns whichever bound owners are chain-like (duck-typed on having a `suspend_updates` method -- naturally filters out `WireSlackHandler`'s own unrelated callback, which has no such method). No point id, no path-table lookup, no clone/canonical resolution needed at all -- whatever object actually bound itself to that exact `Point` instance is exactly what needs suspending. Verified with a standalone test (correct filtering, dead-weakref handled gracefully). **User-confirmed live, 2026-10-17: this fixed it.**

## Line 933-end (`realize_length_change`, `realize_3d_move`) — one evaluation each
Runs once per drag step for length changes and 3D moves, not inside the search. Cost is one `_evaluate_points` plus one `_commit_points`. The same `_chains_for_point` scan applies.

## Line 175-313 (`_reconcile_interior`) — database writes on commit
Inserts points and layouts for new interior positions and removes old ones. Runs once per commit. The `in_progress` flag exists to avoid DB churn while the mouse is still moving (see the module docstring). Fine.
