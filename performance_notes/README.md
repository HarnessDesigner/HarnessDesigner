# performance_notes

Performance notes for the `harness_designer/` package, one `.md` per source file at the mirrored path (`gl/vbo.py` -> `gl/vbo.md`), plus a `README.md` per area where it adds something. Refreshed 2026-11-13: every source file now has a note, notes for code that no longer exists were removed or rewritten, and items that were done are gone.

Numbers marked "measured" were taken on the real classes with throwaway scripts in a sandboxed profile (never the live config or database), on interpreted Python 3.11. The compiled (Cython) build is faster in absolute terms; the ratios between alternatives hold. Everything else is a static read of the code and says so. Speed fixes that cost memory say what the memory is, and say when it may not be worth it.

## Done 2026-11-18: the peg board and schematic housing move and rotate run on pooled storage
The same mechanism as the 3D view for the other two views (`database/project_db/housing_slots_base.py`, `housing_slots_pegboard.py`, `housing_slots_schematic.py`; design in section 15 of the `pjt_housing.py` docstring). Measured with the real classes, the real HEAD cascade against the new one and stand-in tables, a housing of 100 cavities: peg board rotate 489 ms -> 5.9 ms, move 5.6 -> 3.4 ms; schematic rotate 2.4 -> 1.5 ms, move 1.5 -> 0.45 ms; same results to 1.8e-4 mm / 3e-5 (peg board, 1,926 point pairs including 442 clone points) and 1.5e-4 mm (schematic, 54 rotations to exactly 180 degrees, identical callback order). The old peg board cascade left an attached seal's follower stale; that is fixed. Not yet run in the app. What is left is in `database/project_db/housing_slots_pegboard.md`.

## Done 2026-11-14: the 3D housing move and rotate run on pooled storage
A housing's points and angles (its cavities, terminals, seals and accessories) now live in pre-allocated, contiguous pool blocks (`geometry/slot_pool.py`), `Point` / `Angle` hold views of their rows, and the cascade is array math (`geometry/batch.py`, `database/project_db/housing_slots.py`). Measured with the real classes and a stand-in database, a housing of 100 cavities with 100 terminals, 100 seals and 6 accessories: rotate frame 712 ms -> 4.7 ms, move frame 4.7 ms -> 0.93 ms, with the same results as the old cascade (30 random housings x 6 gestures, worst difference 1.8e-4 mm / 6e-5). Not yet run in the app. What is still open for a frame is in `database/project_db/housing_slots.md` (the cache writes every frame, one callback per point, the clone-point SQL once per gesture). The peg-board and schematic cascades were moved onto the same machinery on 2026-11-18 (next entry).

## Done 2026-11-14: the rotation gizmo's protractor rings are built once and moved by one rotation
Each protractor ring (washer, 360 ticks, 36 labels) is now built once in its own frame: the washer is one VBO, all 360 ticks are one VBO (one draw), the outer ring's 360 pick boxes are one array tested in one vector pass, and the labels are placed by array math. Measured with the real classes (interpreted, one inner ring, before -> after): draw 12.0 -> 0.70 ms (25.3 -> 0.58 ms in the 2D views), the object turning 91 -> 1.9 ms, the camera moving 22 -> 0.94 ms, picking 16 -> 0.15 ms, pixel-identical within 32 levels. Before this the gizmo's 91 ms per rotation frame was the slowest part of a housing rotation drag (the housing cascade itself is 4.7 ms). Not yet run in the app. See `rotation_handlers/rotation_ring/_protractor_base.md` for what is left (the labels in the shader, `_disc_rotation` in NumPy, `InnerRing.hit_test`).

## The highest-value items, in order of effect

1. **`geometry/decimal.py` makes `Point` and `Angle` arithmetic 5-100x slower than it needs to be.** `Decimal.__new__` runs `str(float(str(value)))` on every construction, including for values that are already `Decimal`. Measured: `Point + Point` 19 us (3.9 us in NumPy), `Point @ Angle` 66 us, `Angle.from_euler` 650 us, `Angle + Angle` 675 us, `Angle.copy()` 193 us, `Quaternion.as_matrix` 143 us. Skipping the normalisation for `Decimal` input halves the Angle numbers and is drift-safe (it removes a float64 rounding per step, so it is more precise than today). Plain float math is not a general fix because loops accumulate error; the precision-keeping next step is raw `decimal.Decimal` inside `Angle`/`Quaternion` composition, wrapped once at the end. Float is safe only for values derived fresh each time and never fed back. Rotation drags spend their CPU here. No memory cost. See `geometry/README.md`.
2. **Project tables are cached in memory, and `OR` selects scan the whole table.** `database/project_db/table_data.py` holds every row of a project as a dict (about 0.6 KB of dict plus the values per 20-column row, so roughly 11-16 MB per 10,000 rows). An `OR` select returns every row (0.4 us per row, 20 ms at 50,000 rows); it is used when a point is deleted and inside peg-board drag frames. An index union fixes it for a few hundred KB. See `database/README.md`.
3. **Raw SQL for clone points.** The 3D housing cascade now asks once per gesture instead of every frame (`find_child_point_ids`), but the query still scans the whole point table (no index on `parent_point_id`): 15-19 ms at 50,000 points, 2.8-3.9 ms at 10,000. The peg-board cascade still asks on every frame. A cache lookup or an index brings it to 0.1-0.8 ms; the cache version costs 0.8 MB per 10,000 point rows (2.8 MB at 50,000) and also sees rows still pending in the gesture. See `database/project_db/pjt_housing.md`.
4. **The catalog's FK filter columns have no index.** On the real 395 MB database `WHERE family_id=?` on 81,093 housings takes 35 ms; with an index 0.1 ms. Filtered part search is 69 ms, unfiltered 276 ms. Cost: tens of MB of disk, almost no memory. See `database/README.md`.
5. **Schematic drags rebuild the routing frame on every mouse move.** `Generic._route` calls `build_frame` per move (the earlier note said once per drag). The router's grid is 62 bytes per node and supports incremental updates. See `wire_routing/routing.md`.
6. **Peg-board drag solver: up to 18 `_evaluate_points` passes per move** when the move does not fit, each repeating structural lookups. A warm start and a per-drag cache fix it. See `handlers/rope_pull_handler.md`.
7. **Memory held for nothing:** `TubeMixin._twist_plan` keeps about 0.9 KB per wire piece (90 MB for 1,000 wires of 100 pieces) for data the viewport never reads (`objects/mixins/tube.md`); `image/wire_images.py` caches every distinct wire image for ever at 160 KB each (`image/wire_images.md`); `ray_tracing/scene.py` copies each model's mesh per instance (`ray_tracing/scene.md`).
8. **`_PygmentsHighlighter.highlightBlock` lexes the whole document for every block**, O(blocks x size) per edit (`ui/widgets/code_editor_ctrl.md`).
9. **Per-draw `float(str(v))` conversions** in `gl/vbo.py` and `gl/materials/material.py`: about 6 us per draw call on the draw path (`gl/vbo.md`).
10. **Every log line costs about 476 us** (a one-row pandas DataFrame plus `to_csv`) against 2 us for `csv.writer`; a logging burst saturates the log worker (`logger/log_handler.md`).
11. **3D `Wire` / `Bundle._recalculate_geometry` still compute their bounds twice** per path change, and `_segment_transforms` builds an `Angle` (132 us) per segment per call, every frame while a wire is selected (`objects/objects_3d/wire.md`).

## What is already good (do not regress)

The pooled model and wire arenas with one batched draw (`gl/wire_batch.md`: about 200 ms -> 3 ms per frame for 100 wires, measured by the author), the gesture-deferred database writes (`database/project_db/pjt_bases.md`), WAL mode, the singleton short-circuit before existence queries, the compiled A* / twisted-path / loop-search / BVH extensions, suspend/resume of geometry rebuilds around a batch of point moves, and the `chain_cache` in the rope-pull resolvers.

## Reading a note

`## Line a-b (`name`)` headings carry the current line range of the function they discuss (refreshed from the source with an AST pass; re-run it after large edits). Notes that were generated from an AST pass (the per-table database notes, the cold UI/plugin/scraping notes) say what they checked and carry the line "Status: static read of the code only".
