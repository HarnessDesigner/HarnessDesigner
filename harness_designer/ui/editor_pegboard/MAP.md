#### editor_pegboard.py

Defines `EditorPegboard(DockBase)` — the dock wrapper, and `EditorPegboardPanel(gl.canvas_pegboard.CanvasPegboard)` — the GL canvas, for the Peg Board Editor: a top-down "manufacturing formboard" view of the harness (real 3D part meshes reused flat, bundle strands instead of individual wires except bare-terminated ones; see this file's DESIGN NOTES's "Peg Board Editor" entries for the full multi-phase architecture history). Docstrings explicitly describe this file as a "structural mirror" of `editor_3d.py`/`editor_schematic.py` so `mainframe.py`'s per-editor fan-out can treat it uniformly, same dock-creation shape and same thin forwarding methods. `EditorPegboard` also owns `self.wire_highlight` (`objects.objects_pegboard.wire_highlight.WireHighlight`) — lights up in blue whatever a selected wire row (in any wire table: housing, bundle, or transition) touches on the peg board; the actual wire table UI (`WireTable`) lives in the sibling `ui/pegboard_table/` directory, not here. `EditorPegboardPanel.center_on_object(obj)` mirrors `editor_schematic.EditorSchematicPanel.center_on_object`/`editor_3d.Editor3DPanel.center_on_object` exactly, reading the anchor position off `obj.objpegboard` (the peg-board-specific wrapper) rather than `obj` itself. **Drift correction against CODEBASE_MAP.md**: that doc's `ui/` section claims `EditorPegBoard`'s `add_object`/`remove_object`/`set_selected`/`set_clone_obj` are "no-op stubs" because "Phase 1 has no peg-board selection/object model," with real work happening through a separate `load_project(project)` method — this is now stale. `add_object`/`remove_object`/`set_selected` on both `EditorPegboard` and `EditorPegboardPanel` are real, incremental implementations that forward to the inner `gl.canvas_pegboard.canvas.Canvas`, which registers/unregisters `obj.objpegboard` (skipping any object whose peg-board wrapper is inert, i.e. constructed with `vbo=None`); there is also no `load_project` method defined on this file at all — bulk loading is inherited from the base `CanvasPegboard`/`Canvas` class in `gl/canvas_pegboard/`, not overridden here. Only `set_clone_obj` is still a genuine, documented no-op ("Phase 1 has no clone/paste model for the peg board yet" — `EditorPegboardPanel.set_clone_obj`'s own docstring/body is just `pass`). This dock depends on `objects_pegboard/wire_highlight.py` (outside this directory) and on `gl/canvas_pegboard/` for the actual GL rendering/anchor collection — it is a thin UI wrapper, not where the peg-board rendering logic lives.

#### Peg Board Editor: design decisions and what the table experiments found (2026-07-13 to 2026-09-14)
A manufacturing-formboard view (`ui/editor_pegboard/`, `gl/canvas_pegboard/`): the harness laid out flat and top-down, real 3D part meshes reused through the shared VBO/arena system (OBB-derived flattening in `gl/canvas_pegboard/flatten.py`, anchors via `layout_graph.py`), bundle strands instead of individual wires (except bare-terminated wires), user-repositionable with a length-budget clamp, plus floating spreadsheet-style wire tables at branch points/connectors/bare terminals. The original isolated `pjt_pegboard_points/waypoints/tables` overlay design is gone (see `database/project_db/MAP.md` for the replacement DB layer); `pjt_pegboard_tables`/`table_point_peg_id`/`TablePositionPegMixin` (a table's own position) is a separate concept and was left alone.
- **Locked decision:** drag repositioning uses a local per-segment length clamp only, no FABRIK/rope-relaxation solver (the later `rope_pull` package is the length-budget mechanism that grew from it). Do not re-litigate.
- **Tables:** the floating tables are real Qt widgets rendered off-screen and shown as world-space GL textures (`ui/pegboard_table/`, `mdi_host.py`: a `QMdiSubWindow` in a `QMdiArea` with `WA_DontShowOnScreen`, `.grab()` re-uploaded through `gl/shaders/texture`), chosen over a from-scratch GL-drawn table. A screen-space `QTableView` repositioned every frame looked wrong when zooming; a texture on a world-space quad scales with the camera by construction. Raster means blur at high zoom (a resolution-tracks-zoom re-grab was not built).
- **Why not hand-drawn GL tables (POC in gitignored `scratches/pegboard_spreadsheet_widget/`):** it worked (pinned header, scroll bars, resize, wire icons as textures, SDF rounded rects) but needed theme-colour guessing and hand-rolled chrome. Its performance was dominated by PyOpenGL call count (`shapes.text.Text` issues one draw call per character); phrase-VBO batching (merge a unique string's glyphs into one cached VBO) gave ~23x, Cython compiling gave nothing, and layout-math caching was not worth it (microseconds). Pitfalls worth keeping: a pinned header over a scrolling body needs its OWN glScissor regions (one shared rect leaves the internal boundary unclipped); programs ref-count their own `glUseProgram` binding, so group draws by program rather than interleaving two different program objects inside one `with`; a cache sweep tied only to the miss path starves on a mostly-hit workload.
- **Rules from the texture approach (still apply to `mdi_host.py`):** (1) a `WA_DontShowOnScreen` widget that is repeatedly `.grab()`bed still needs one explicit `.show()` after construction, or its scroll-area geometry never settles and the untouched scroll bar flip-flops; (2) native interaction is driven by dispatching synthetic Qt events to the right sub-widget (`panel.childAt(point)`), emulating the implicit mouse grab (capture the press target once; every move/release goes to it; moves must report the held button); (3) send a hover `MouseMove` at the exact target BEFORE a press (`QMdiSubWindow` hit-state comes from the move, not the press); (4) keep the `QMdiArea` large (2000x1400) and `grab(rect)` only the sub-window, because a parent sized exactly to its child blocks the child from growing; (5) sub-window drag is converted into the canvas's world-space anchor (`_sync_panel_geometry`); (6) if Qt shows odd-looking but stock `QAbstractItemView` behaviour (scrolling to the current cell), confirm it is a Qt default and leave it, per the user.
- **Palette roles on this machine's Windows 11 style are unreliable for flat fills:** `AlternateBase` reads as black and `Button/Text/ButtonText` have alpha under 255 from a bare palette. Force alpha to 255 in the one place colours pass through and derive the odd-row colour by blending `Base` toward `Text`; verify a role by sampling a real render, not by its documentation.
