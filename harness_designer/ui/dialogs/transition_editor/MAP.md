## FILES

#### __init__.py

Re-exports `TransitionEditorDialog` only.

#### dialog.py

`TransitionEditorDialog(BaseDialog)` -- the dialog itself. Three entry modes: **Select Existing** (edit a catalog transition in place), **New** (insert a fresh row with a placeholder part number `NEW-<8 hex chars>` and every FK defaulted to the catalog's seeded `NIL_ID` (`b'\x00' * 16`) "Unknown"/"No X" rows -- a real, already-populated placeholder, not a dangling reference, so don't treat these defaults as a bug if you see them referenced), and **Load As Template** (clone an existing transition plus every one of its branches under a new `<part>-COPY-<6 hex chars>` part number via `_clone_transition`, then load the clone so edits never touch the original from the very first keystroke). Reuses the catalog's own shared `TransitionsTable.control` (`TransitionControl`/`TransitionBranchControl`, the per-table singleton control documented in `ui/prop_ctrls/MAP.md`), reparenting it into the dialog for as long as it's open and back onto the mainframe (hidden, unbound via `set_obj(None)`) on close -- `self._control = parent.global_db.transitions_table.control`, released by `_release_control()` (disconnect the two signals it connected, `set_obj(None)`, `hide()`, reparent back onto the mainframe), which `accept()`, `reject()`, and `closeEvent()` all call before `self.canvas.cleanup()`. Any new exit path added to this dialog must do the same, or the shared control will leak its last-bound transition and/or stay reparented away from the mainframe. Has its own self-contained `_Config` (lighting/renderer/background settings for its own `Canvas3D`) and its own `bounds.Manager`, modeled structurally on `ui/dialogs/part_orientation.py` rather than on the original validation prototype at `scratches/transition_viewer/transition_editor.py` (that prototype's job -- fixing 111 existing bad catalog rows -- is done and already merged into the live catalog). A branch-field edit debounces into `_rebuild_preview` via a 150ms single-shot `QTimer` (typing/dragging a spin box can fire many `propertyChanged` signals in a burst; only the last one within the window actually triggers a rebuild). Also tracks `_last_branch_tab_index` so switching to a different transition restores the previously-active branch tab (clamped to the new part's branch count) instead of always resetting to tab 0. Full design background and the decision log (including the stage-6 branch-level drag interaction, not yet built) are in `TRANSITION_EDITOR_DIALOG.md` at the repo root -- read it before making further changes here, per that doc's own instruction echoed in MEMORY.md's "Transitions" entry.

#### preview.py

`PreviewTransition(ObjectBase)` (non-selectable wrapper, same role as `part_orientation.py`'s `PartModel`) and `PreviewTransition3D`. Unlike `part_orientation.py`'s `PartModel3D` -- which has to be a from-scratch `Base3D` subclass because that dialog previews every catalog part type generically -- `PreviewTransition3D` **subclasses `objects_3d.transition.Transition` directly**, since this dialog only ever deals with transitions: it overrides only `__init__` (to source data from a catalog `Transition`/`TransitionBranch` instead of a placed `PJTTransition`) plus `set_selected`/`delete` (no-ops) and `handle_interaction` (always returns `False` -- the preview never moves or rotates on its own; it always sits at the origin with identity angle, and the dialog's own camera controls are how the user looks at it from another angle). `__init__` calls `base_3d.Base3D.__init__` directly rather than `super().__init__()`, deliberately bypassing `Transition.__init__` (which is `PJTTransition`-specific). `rebuild(part)` is called whenever a branch field changes, `branch_count` changes, or a different transition loads: it evicts the part's cached body VBO (`PooledVBOHandler.evict(part.part_number + ':transition')`, since this dialog is the one place a catalog part's bulb geometry can change under an unchanged `part_number`), rebuilds `self._body.branches` from scratch if the branch count changed (a real placed `Transition`'s `branch_count` can never change post-placement, but editing it is this whole dialog's purpose), then calls the inherited `build()`.
