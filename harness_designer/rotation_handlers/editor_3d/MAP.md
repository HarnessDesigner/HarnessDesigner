## FILES

#### __init__.py

Package docstring only, explaining why there's no per-object-type split yet (kept `generic.py`-first, mirroring `drag_handlers.editor_3d`'s own generic/specific split, so a future object type needing bespoke rotation behavior has a place to live without restructuring this package again) — this is the one implementation every rotatable 3D object type currently shares.

#### generic.py

`Rings3D(Base3D)` — owns three per-axis `rotation_ring.RotationRing` gizmos and their pick/activate/drag/snap interaction: `pick` (which torus ring is under the mouse), `activate`/`deactivate` (show/hide a protractor, dim the other two), `begin_inner_drag`/`update_inner_drag`/`end_inner_drag` (free-rotation drag on the inner ring), `update_outer_hover`/`click_outer_snap` (hover-highlight + click-to-snap on the outer ring's ticks), `apply_drag_angle` (write a drag-driven Euler value without re-triggering itself). This is what `rotation_rings.RotationRings` (the facade) holds as its own `obj3d`. `Rings3D._on_obj_angle`/`_on_obj_scale` are bound callbacks on the tracked object — every ring's orientation/size is re-derived from the object's live state, not cached independently; don't introduce a second source of truth for "where is this gizmo right now." `_update_position` deliberately tracks gizmo position WITHOUT `Base3D`'s own world-space floor-lock logic (same pattern used by `drag_handlers.move_arrows.Arrows3D`/`wire_marker_arrow.ArrowMarker3D`) — a gizmo object following its tracked target is not subject to the same ground-plane constraints a real placed object is. **Centers (2026-10-25):** an ordinary object's rings are centered on its own `position` Point, shared and never copied; a wire service loop's are centered on its CENTROID (`WireServiceLoop.centroid`), a Point of the gizmo's own that `_sync_center` keeps current (bound to the loop's angle and position). A loop turns about its centroid, and `WireServiceLoop._update_angle` does that by moving the start point (its `position`) to keep the centroid still, so rings centered on the position orbited the centroid on every rotation, the washer and torus following the moving Point live while the ticks and labels (baked in world space) stayed behind. `_update_position` now also re-bakes the rings (`_refresh_rings`), and `ProtractorRingBase.reposition_all` skips only when the center is unchanged too. The class is built from overridable hooks (`_ring_axes`, `_make_center`, `_make_ring_angle`, `_ring_material`, `_bind_object`/`_unbind_object`, `_HAS_TORUS`) so `wire_roll.WireRollRings3D` can reuse all of its pick/drag/snap code.

#### wire_roll.py

`WireRollRings3D(Rings3D)` — the single ring that rolls a wire service loop about the wire it sits in (the loop's "Rotate on Wire" context-menu entry; armed through `rotation_rings.WireRollRings`, not by the right-click that arms the ordinary gizmo). One Z ring, no torus (the protractor is active from the start), centered on the PIVOT (where the line through the two wire points either side of the loop meets the line between the loop's start and stop points) in the plane perpendicular to the wire. Neither moves when the loop rolls, so the ring is fixed and only its protractor spins. It reuses the ordinary pick/drag/snap code by handing the rings a private `Angle` instead of the loop's: its X/Y Euler values tilt the ring's plane perpendicular to the wire (`ex = -asin(ay)`, `ey = atan2(ax, az)`, checked against `rotation_mesh.slot_normal`), and its Z Euler value IS the roll in degrees from the pose the loop had when the ring came up; `apply_drag_angle` rolls the loop to it through `WireServiceLoop.roll_to` (always from that frozen starting pose, so nothing drifts and 0 on the protractor means back where it began; no collision search). Sized from the farthest corner of the loop's box from the pivot, which a roll about a line through the pivot never changes, so the ring never resizes.
