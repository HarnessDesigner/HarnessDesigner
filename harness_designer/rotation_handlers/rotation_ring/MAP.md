## FILES

#### __init__.py

(Its module docstring has a short "How the gizmo stays fast" section; the full description is the docstring of `_protractor_base.py`.) `RotationRing` — assembles one axis's `TorusRing` + `InnerRing` + `OuterRing` into a single unit and owns the show/hide/pickability state machine between them. Initial state: only the torus ring is visible/pickable; `try_activate()` shows the protractor (inner+outer) and dims/depickables the torus; `set_dimmed()` dims a SIBLING axis's torus (called by whatever owns all three axis instances, since dimming a sibling is inherently a cross-axis decision this class can't make alone). This package holds the shared ring/protractor building blocks used by every view's rotation gizmo (`editor_3d`, `editor_pegboard`, `editor_schematic`) — the torus activation ring, the object-space and world-space protractor rings, the disc+tick+label geometry they both build on, and the per-tick pickable wrapper. It lives one level ABOVE `editor_3d`/`editor_pegboard`/`editor_schematic` (as `rotation_handlers.rotation_ring`, a sibling, not nested under any one view) specifically because it's shared across all three — the per-view `generic.py` modules each build `RotationRing` instances from here rather than each view having its own ring implementation.

#### _hit_test.py

`point_near_segment` — small screen-space hit-test helper shared by the ring/tick pick tests.

#### _protractor_base.py

`ProtractorRingBase` -- one protractor ring's washer, 360 ticks and 36 degree labels, shared by `inner_ring.py` and `outer_ring.py`. **The module docstring is the full description of how it works (read it before changing anything that draws, places or picks a tick or a label); this entry is the summary.** The ring is a rigid object, so it is built ONCE in its own frame (centre at the origin, ring plane XY, +Z the normal, tick `i` at `i` degrees) and only ever carried to the world by the shared `center` Point and the ring's rotation: the washer is one VBO; all 360 ticks are ONE VBO (`_ticks_vbo`, 8-sided prisms placed, sized and aimed by three `einsum` calls, tick `i` owning vertices `[i*V, (i+1)*V)` so the hovered one can be drawn on its own in red); the outer ring's 360 pick boxes are three arrays (`_box_centre_l`, `_box_axes_l`, `_box_half`); the 36 labels are placed by array math (`_update_labels`: a cylindrical camera-facing billboard in 3D, lying along their tick in the 2D views, composed after `local_tilt`), never through `Text.render`. A frame is the washer, one tick draw (three while a tick is hovered) and 36 label draws, all through `VBOHandlerBase.render_raw`; there is no per-tick `Point` or `Angle` any more. Measured (interpreted, one inner ring): draw 12.0 -> 0.70 ms, the object turning 91 -> 1.9 ms, the camera moving 22 -> 0.94 ms, picking 16 -> 0.15 ms, pixel-identical to the old code. **`reposition_all` must be called whenever the ring's orientation or the centre changes** (it skips itself when neither did; `Rings3D._update_position` calls it for a moved centre); a subclass's `__init__` calls it once and then `start_camera_tracking`. The radii live in `_recompute_local_geometry` / `set_radii` (the only things that rebuild a mesh). The labels' world positions are the only world-space data the ring holds (`_label_rel` + the live centre).

#### inner_ring.py

`InnerRing(ProtractorRingBase)` — the object-space protractor ring; its own-slot spin tracks the object's current Euler value for this axis directly, so its `0` tick always points at the object's own local zero. Grabbing anywhere along its band and dragging free-rotates the object about this axis — replacing the OLD fixed-handle drag in the retired `rotation_handlers/rotation_rings.py`'s `DragRotate`.

#### outer_ring.py

`OuterRing(ProtractorRingBase)` -- the world-space protractor ring; its own-slot spin is held fixed regardless of drag (nests under the other two axes like every other ring -- the "gyroscope" behavior -- but this axis's own Euler value is zeroed before computing the plane, so its `0` tick never moves even while the inner ring/object spin past it). Owns hover-highlight/click-to-snap. **Picking is `pick_tick_index`: a real ray against each tick's own oriented box, done for all 360 at once** -- the boxes are the base class's three ring-frame arrays, carried to the world with the ring's matrix (one matmul each) and tested with the vectorised slab test (the same test as `gl.object_picker._ray_intersect_obb`, over arrays; 0.15 ms against 16 ms for the per-box loop alone). Nothing about a box is stored in world space, so nothing can be stale and there is nothing to resync on a reposition. The hovered tick is just `_hovered_index` (the base `render` draws it in `_HOVER_COLOR`); `hovered_degrees` / `click_hovered` are derived from it. Easy to misread as a bug if you are not expecting the nested-Euler "gyroscope" convention -- see `rotation_handlers/MAP.md`'s module-level description of the `Ry*Rx*Rz` ordering before changing the plane math.

#### torus_ring.py

`TorusRing` — the always-visible, click-to-activate ring for one axis. Round-tube cross-section (unlike the flat disc rings) because a torus tube only stays circular under uniform scale, and this ring's diameter must match whatever object it's wrapped around — builds its own sized mesh rather than reusing the shared unit VBO the disc-based rings use. Clicking anywhere on the band activates that axis's protractor.

## DESIGN NOTES

Lasting rules and design notes moved here from the repo-root `MEMORY.md` on 2026-11-01 and trimmed the
same day: bug-fix narratives were dropped (git history has them), keeping only what still constrains
the code. Point-in-time -- verify claims against the current code before relying on them.

#### The protractor rings are built once in their own frame (2026-11-14)
The rule that still constrains the code: a ring's ticks, pick boxes and label offsets live in the ring's own frame, as arrays and GPU buffers built once (and rebuilt only when the radii change); the ring is moved to the world by the centre and one rotation, never by per-tick objects. Nothing per tick may be a `Point` or an `Angle`, and nothing may loop over the 360 ticks in Python on an angle change or a frame. The 36 labels are the only per-object draws left. The full description, the invariants and the measurements are the module docstring of `_protractor_base.py`. Open: the labels could be billboarded in the vertex shader (proven pixel-identical in a throwaway prototype, `performance_notes/rotation_handlers/rotation_ring/_protractor_base.md`) which would also remove their 36 draws; `InnerRing.hit_test` still projects 130 points per mouse move with `Angle @ array` (`inner_ring.md`).

#### Rotation-ring redesign direction (discussed 2026-08-17; the protractor gizmo has since been rebuilt)
The direction the user wanted for `rotation_ring`: a physical-protractor look (disc, tick marks and numbers, pointer arm), muted ring colours and smaller diameter via `Config.rotation_rings`, a translucent (~0.1-0.2 opacity) light-blue glowing disc plus a 0-degree reference line on the dragged axis (`GlowingMaterial`, `floor.py`'s `GL_BLEND` pattern, `HANDLE_LOCAL_DIRS[axis]`), and NO small grab-handle spheres: the ring itself is the drag target, because a single-point handle can sit on the far/occluded side of the object while some part of a full ring is always visible. Consequence for picking: the blanket `RotationRings` exclusion in `MouseHandlerBase._pick_exclusions()` must be selective (a click on the ring band registers, a click past it falls through to the object behind). Check the current code for how much of this was built.
