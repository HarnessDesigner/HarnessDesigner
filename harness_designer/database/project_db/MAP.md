## FILES

#### __init__.py

Package init for `project_db`; no real logic of its own. Per-project tables, all prefixed `pjt_` — the placed-instance layer of the "same-name modules" pipeline (`create_database` → `global_db` → `project_db` → `objects/`, see `database/MAP.md`): a `pjt_*` row holds position/angle/scale plus a `part_id` FK into the matching `global_db` catalog part, and holds a weakref to its live scene object (`get_object()`/`set_object()`).

#### circuit_solver.py

The electrical AND thermal model of one circuit, as pure code (no database, no Qt), so it can be tested alone and changed in one place. `solve_circuit(children, parts, loads, volts, return_type)` takes the tree `PJTCircuit._trace` walks out from the voltage terminal, a `PartData` per member (resistance at 20 C, temperature coefficient, thermal resistance to the air, ambient temperature, rated maximum) and a `LoadData` per load terminal (rated amps and a `LoadType`), and returns a `CircuitSolution`: current and entry voltage of every member, what each load draws, each member's temperature and rise, `over_temp` (hotter than rated; an unrated part is never flagged), `runaway` (cannot shed its heat) and `converged`. The model: an ideal source (its own resistance is not in the circuit, though it heats); every wire/splice/loop/load terminal a series resistance AT ITS OWN TEMPERATURE `r20 * (1 + alpha * (T - 20))`; a load is its rated current at the circuit voltage reacting to the voltage that really reaches it (`RESISTIVE` draws less as the voltage sags, `CONSTANT_CURRENT` the same, `CONSTANT_POWER` more); a part heats by `theta * I^2 * R(T)`, solved exactly for the rise; the return path is the circuit's `ReturnType` (`CHASSIS` not modelled, `MIRRORED` doubles every series resistance). It solves bottom-up with each branch reduced to an affine `(g, c)` pair (current = g*V + c), then top-down, and repeats until the temperatures and constant-power currents stop moving (`converged` is False when they do not, or a constant-power load is starved of voltage). Constants that are CALCULATIONS rather than data and are not calibrated yet: `WIRE_HEAT_TRANSFER` (10 W/m^2K), `CONTACT_THERMAL_RESISTANCE` (40 K/W), `COPPER_ALPHA`, `DEFAULT_AMBIENT_C` (20). `calibrate_theta(limits, r20, alpha, rated_max_c, ambient_c)` turns a manufacturer's derating rows (`(ambient, max amps)` pairs) into a thermal resistance: a part carrying its limit is at its rated maximum, so `rated_max - ambient = theta * I^2 * R(rated_max)`; the limit is interpolated at the part's ambient (0 A at the rated maximum, the coolest row holding below the table) and `None` means the table cannot say, so the calculation is used. Fed back through `temperature_rise` it lands exactly on the rated maximum at the limit. Deliberately NOT here: how a part gets its `PartData` (that is each row's `part_data()`, which reads the part's derating table), and the bundle ambient adjustment (not built). Checked with hand-worked circuits for every load type and against 2,681 random circuits whose every equation (voltage drops, current balance, each load model, the temperature relation, the flags) is verified. WIRES SIDE BY SIDE (2026-10-24): `solve_circuit(..., parallel)` takes groups of wires joining the same two junctions; a group is one series resistance 1/sum(1/R) and its current divides by conductance, each wire then heating from its own share. BUNDLES (2026-10-24, not run in the GUI): `BundleType` (derived, never stored), `BundleData`, `CircuitInput`, `bundle_adjusted_parts` (a wire's ambient rises by the OTHER wires' heat per metre over the bundle surface pi*D*h, warmest bundle wins; a manufacturer bundling table instead divides theta by factor^2) and `solve_bundled` (solves every circuit that shares a bundle together, to a fixed point). UNCALIBRATED: `BUNDLE_HEAT_TRANSFER` (10) and `BUNDLE_PACKING_FACTOR` (1.0 for both types).

#### pjt_bases.py

(~1100-1900 lines) Base classes for every `pjt_*` row/table: `PJTEntryBase`/`PJTTableBase`/`PJTTables`, mixing in `common_db.callback.CallbackMixin`. `PJTTables` exposes one `pjt_*_table` accessor per project table (e.g. `pjt_concentrics_table`, `pjt_pegboard_tables_table`). Row ids come from `database/id_generator.py` (SQLite, client-side) or the MySQL server's `next_project_row_id` (see MEMORY.md's "Project row-id collision safety" note). Also owns `_schema_dependency_order()` — a topological sort of every `create_database` module's own SQL table name, computed once and cached, derived from each table's `SQLField.references` metadata, so a batched multi-table insert can always visit a parent table before a child that holds a foreign key into it. This is deliberately NOT the same as `PJTTables._ordered_project_tables`'s own hand-picked list (which exists only for `load()`'s plain reads, where ordering doesn't matter) — that list has a known gap (`pjt_bundles` references `pjt_points3d` but is visited before it there), which is exactly why the real dependency-ordered version exists for actual cross-table inserts.

#### pjt_circuit.py

`PJTCircuitsTable`/`PJTCircuit(PJTEntryBase, NameMixin, NotesMixin)` — a per-project circuit record (`pjt_circuits`) plus the `PJTCircuitControl` property widget used on the wire/terminal/splice/service-loop panels. The table has `get_by_num`/`get_by_name`/`next_circuit_num` lookups and `members_changed(*circuit_ids)`. The row caches its member id lists (wires, service loops, splices, terminals, and the start/load split of the terminals) and `members_changed` drops them: every wire/splice/terminal/service-loop `circuit_id` setter, `insert` and `delete` (plus a terminal's `is_start` setter) calls it, so a NEW code path that changes a row's `circuit_id` without going through those setters leaves a stale list. `invalidate_members()` also fires `_populate('members')`, so anything bound to the row's `'members'` tag (the object browser's circuit listing) hears every membership change. The member properties read their cache attribute into a local once (`ids = self._stored_x_ids`), never twice, because the circuit editor dock reads a circuit from a worker thread while the UI thread can invalidate it. `label` is the user-facing name (`#3 Fuel pump`, `#3` while unnamed). `PJTCircuit.delete()` clears `circuit_id` on every member in one gesture before deleting its row. `add_member(row)` is the one way to put a wire/splice/terminal/service loop into a circuit: a terminal joining is demoted (`is_start=False`; new terminals insert as `is_start=1`) and promoted again only when the circuit has no start terminal and the terminal has no load. `merge_from(other)` moves every member of `other` in (demoting its start terminals when this circuit already has one); delete the emptied row through `Project.merge_circuits`, not directly. `PJTCircuitControl.set_obj(host)` takes the HOST row (the wire/splice/terminal/service loop whose panel it sits in), not a circuit: picking or typing a circuit number or name assigns the host via `add_member`, creating the circuit through `Project.create_circuit` when none matches; description and notes are disabled while the host has no circuit. Rollups (`resistance`, `total_circuit_load`, weights, lengths) are recomputed on every read from the cached member rows. `circuit_map`/`get_circuit`/`get_circuit_end_terminals` walk the circuit as a tree rooted at the start terminal (`_walk_circuit`, a pure function at the top of the file; `PJTCircuit._trace` reads the ports from the table caches): terminals own `attach_point3d_id`, splices own their start/stop/branch points and are hubs, loops own start/stop, and a wire joins the junctions at its two end points. Each wire and junction is visited once, so a loop in the wiring is cut where it closes; members not wired to the start terminal are not in the map. Nothing calls these yet. Known open problems (see MEMORY.md "Circuits"): `total_circuit_load` skips the volts/resistance term when the circuit's resistance is 0 (a circuit with no start terminal has volts 0.0). The bottom-of-file `pjt_housing` import is unused now that `housings` is gone; left in place because this module's import order is load-bearing for the circular imports above it. `solve()` feeds the walk's tree and every member's `resistance` (0.0 where the part has none) and each terminal's `load` to `circuit_solver.solve_circuit`; `total_circuit_load` is the current drawn from the voltage terminal, `load_at(target)` the current through a wire/splice/loop (or what a terminal itself draws) and `voltage_at(target)` the voltage where it is entered. They re-solve on every call (nothing is cached: resistances depend on live wire lengths), which the peg-board wire table pays for once per circuit column per cell. `return_type` (a `circuit_solver.ReturnType`, column `return_type`, default chassis) is set from the "Return Path" combo on `PJTCircuitControl`'s General page (disabled while the host has no circuit); `solve()` passes it to the solver, `PJTCircuitsTable.insert` takes it, and the "Total Circuit Resistance" readout is still the plain sum of the members (it does not double for a mirrored return). `solve()` asks each member for `part_data()` and each terminal for its `load`/`load_type`, and passes them to the solver; `temperature_at(target)` is how hot a member runs, `over_temperature_members()` lists the members hotter than rated (judged on the air alone for a member the circuit does not reach, or when there is no voltage terminal), and the Electrical page of `PJTCircuitControl` shows the host row's Operating Temperature (editable), Part Temperature, Rated Maximum and Temperature Status, plus a count of parts over temperature in the circuit. `_walk_circuit` still cuts a closing wire; `_parallel_wires` finds the ones joining the same two junctions as a tree wire and `_trace_full` returns them (`_trace` is its two-value form). `_prepare_solve` collects one circuit's solver input, `_bundle_component` finds the circuits that share bundles, and `_solve_traced` solves them together when there are any (a circuit in no bundle is solved alone as before). A ring through 3+ junctions is still cut. The control's Name and Circuit Number fields are `ComboBoxProperty` controls; `_on_name`/`_on_circuit_num` create a circuit for a value no circuit has, so the control must send its event only on Enter or a list pick (it used to send one per keystroke and made circuits `n`, `ne`, `new`, ... in the user's project; fixed 2026-10-24 in `ComboBoxProperty`). `_on_name` uses the name exactly as typed: spaces are never stripped. **A circuit reaches the whole connected chain (user, 2026-10-25):** when a circuit is added to, or changes for, a wire, splice, wire service loop or terminal, every object connected to it takes the circuit too, whatever it was in. `PJTCircuitsTable.connected_members(member)` walks the chain with `_walk_circuit` over the whole project's connection points (`attach_point3d_id` on terminals; `start/stop/branch_point3d_id` on splices; `start/stop_point3d_id` on loops and wires), and `PJTCircuitsTable.propagate(member, circuit_id)` moves what is not in the circuit yet through `PJTCircuit.adopt`, in one gesture. The four `circuit_id` setters call `propagate` when the value changes to a circuit, so any path that sets one spreads; `add_member` and `merge_from` pause it (`propagation_paused`), place their own members first (the start-terminal rule included), then call it once. Setting `None` (what `detach_members` does) never spreads. `adopt` keeps the one-start-terminal rule: a start terminal that joins is demoted, and if the circuit has none afterwards the first former start terminal that carries no load is promoted. Moving members out of other circuits is silent at this layer; the dialogs live in the handlers (`handlers/wire_circuit.py` asks before a new wire merges two circuits, now looking at the whole chain), and the circuit control asks too: `PJTCircuitControl._confirm_move`, called by `_on_name` and `_on_circuit_num`, counts the connected objects that are in OTHER circuits and asks Yes/No (naming those circuits and the target; answered 2026-10-25). It asks BEFORE a circuit is created for a new name or number, so No leaves no empty circuit behind (it only refreshes the control), and it asks nothing when the part is already in the chosen circuit or the rest of the chain is circuit-less or already in the target. `wire_weight_lb` counts the wire service loops like `wire_weight_g` does (2026-10-25; it used to sum the wires alone, so the pound total disagreed with the gram total).

#### pjt_pegboard_table.py

`PJTPegboardTablesTable`/`PJTPegboardTable(PJTEntryBase, PositionPegboardMixin, VisiblePegboardMixin)` — the CURRENT, real Excel-like data-table-overlay row (`pjt_pegboard_tables`), one row per anchor (housing/bundle/transition — a transition gets exactly ONE table for all its branches, not one per branch) that has a floating peg-board wire table. Its own `position_pegboard` is deliberately the SAME `pjt_points_pegboard` row as the owning anchor's own `table_point_peg_id` (`mixins/table_position_peg.py`'s `TablePositionPegMixin`, mixed into every anchor type that can own one of these), not a fresh point of its own — sharing that one point is what lets `PJTPegboardTable.anchor` and `PJTPegboardTablesTable.get_from_point_pegboard_id` find one row from the other by plain equality lookup, in either direction, with no forward FK on either side. Created at a fixed, deliberately elevated `Y` (`TABLE_DEPTH_Y = 50.0`, peg-board X/Z are the screen's two axes under a top-down camera, Y is depth/render order) so a table always renders on top of ordinary anchors/wires/bundles beneath it, and at a naive default size (`DEFAULT_TABLE_WIDTH`/`HEIGHT` = 100.0/50.0 world mm) since insert-time has no live view/AABB data to run an obstacle-avoiding placement search — a user can resize it afterward via its own MDI sub-window edges. This is a separate, surviving concept from the OLD isolated `pjt_pegboard_points`/`pjt_pegboard_waypoints`/`pjt_pegboard_tables`-as-overlay design referenced in old planning notes, which has been fully superseded by the mixin-based peg-board DB layer (see `mixins/MAP.md` and MEMORY.md's Peg Board Editor entries) — don't confuse the two; this file IS the current, real table.

#### pjt_terminal.py

`PJTTerminal` — a placed terminal instance. `PositionPegboardMixin`/`AnglePegboardMixin`/`VisiblePegboardMixin`; leaf (no cascade of its own, matches the 3D view). `sync_free_wire_points(view)` re-derives its crimp/back-face points (+ `parent_point_id` children) from position/angle for a cavity-less (free-standing) terminal — a no-op for seated terminals (cached `self.cavity` guard keeps the seated path free of SQL). `_create_free` (shared by `add_at_wire_end`/`add_free`) builds one; a 3D-placed free terminal gets a pegboard `(x, 0, z)` position and vice versa, like housings. #### pjt_wire_path.py

`PJTWirePathsTable`/`PJTWirePath` for `pjt_wire_paths` (NEW 2026-09-26, untested) — one row per INTERIOR waypoint per wire per view (`wire_id`, `idx`, exactly one of `point3d_id`/`point_pegboard_id`/`point2d_id`, plus optional `bundle_id`/`concentric_id`/`transition_id`/`transition_branch_id` tags; a wire's start/stop stay columns on `pjt_wires`). Rows reference SHARED point rows, so `idx` lives here, not on the point. THE source of truth for every wire waypoint index: everything writes through `add`/`append`/`remove`/`set_route` (which renumber in one `batch_update`), and `PJTWire.waypoints3d`/`waypoints2d`/`waypoints_pegboard` read from it. Also the (not-yet-written-to) source of truth for which bundle/transition-branch a wire runs through, via its `bundle_id`/`transition_branch_id` tags — see `pjt_transition.py`. `_route_rows` (so `point_ids`, `for_wire`, and through them every wire's `length_mm`) is an index lookup on `wire_id` since 2026-10-24, no longer a scan of every route row in the project; see `table_data.py`.

#### pjt_wire_service_loop.py

`PJTWireServiceLoop` — a placed wire-service-loop instance. `AnglePegboardMixin`/`StartStopPositionPegboardMixin`/`VisiblePegboardMixin`, leaf. `load`: the current through the loop, from the circuit solver. Has the `operating_temp` column (NULL = nobody has set one) and the temperature API of `OperatingTempMixin` (`WireOperatingTempMixin` for a wire or loop): `ambient_c`, `max_temp_c`, `part_data()`, `temperature_c`, `over_temperature`; see `mixins/MAP.md`. `resistance` is `_resistance_over(self.length_mm)`, as on `PJTWire`, so `part_data()` computes the length once. **`length_mm` corrected 2026-10-25:** it is the centre-line length of the loop that is DRAWN (`shapes/cylinder_helix.create_vbo`), worked out from the wire diameter alone (no constants), in wire diameters: the helix's radius is one wire diameter (`Helix(radius=diameter, ...)` where `diameter` is the wire's), so the wire's centre track is TWO wire diameters across (the coil's inside diameter is one, its outside diameter three); pitch 1.15; one turn; and a straight lead-in and lead-out of one wire diameter each, added as `diameter * 2.0`. That is 8.39 x the wire's outside diameter. It used to be 4.35 x: the formula took the helix's diameter to be the wire's own and counted only one straight piece. The loop's weight and resistance, the solver and the circuit editor's totals all follow it. If the mesh's helix or straight pieces change, change the constants (a comment in `create_vbo` says so).

#### project.py

`Project` — the project table itself (one row, project-wide metadata: `model_id`/`color_id` for the optional project model, no position/scale/angle columns of its own — "Add/Edit Project Model" sets file + color but the model stays at the origin).

#### pseudo_bundle_layout.py

`PseudoPJTBundleLayout(PJTBundleLayout)` — an in-memory-only stand-in for a `PJTBundleLayout` row, used while a peg-board drag needs a waypoint that doesn't have a real row yet. Constructed directly with `table=None` and a throwaway `db_id`, never through `PJTBundleLayoutsTable`; every database-backed property is overridden to return in-memory state set by `configure()`, and setters are no-ops, so nothing is written back to the database — the real rows are written only when the drag releases. Mirrors `pseudo_wire_layout.py`'s `PseudoPJTWireLayout`, but unlike that one, visibility IS configurable here (a drag waypoint is meant to be seen, whereas a wire-snap probe must stay hidden).

#### pseudo_wire_layout.py

`PseudoPJTWireLayout(PJTWireLayout)` — an in-memory-only stand-in backing an invisible wire-snap probe. Wire snapping (onto a terminal's attach point, a splice's branch point, or another wire's dangling end) used to only work when the pick ray happened to intersect the target's exact mesh geometry; the fix reuses `objects.wire_layout.WireLayout` itself as the pickable hit-test target (it already renders as a sphere sized to the wire's own `od_mm` and is already recognized by every hover/click branch), so `handlers.wire_snap.SnapProbeSet` builds one of these at every snap-allowed location. This module supplies the one piece both consumers (`handlers.wire_handler.AddWireHandler`, `gl.canvas3d.dragging.EndpointDragObject`) needed: something satisfying `PJTWireLayout`'s type contract while never touching a real database row.

#### table_data.py

`TableData` — one project table's cache (`WRITE_DESIGN.md` section 4). One load per project, reads from memory, changes recorded per row and column, inserts and deletes cancelled or queued, and the flush's `DELETE`/`INSERT`/`UPDATE` statements built from the cache. `RowDeletedError` is raised on a read or change to a deleted row. `RAW_DELETE_IMMEDIATE` selects the immediate or deferred delete path. Project tables only; not yet wired into `PJTTables` for the general case. Distinct from the still-planned, NOT-yet-built per-gesture write manager described in MEMORY.md ("Write manager for drag/rotate persistence") — that one is a `with`-scoped deferral of every mouse-move's DB write to one batched transaction at gesture end, a different mechanism from this row-cache-and-flush design. Since 2026-10-24 a `select` that names columns is answered from a LAZY PER-COLUMN INDEX instead of looking at every row: the first time a column is asked about (on a table of 32 rows or more) its values are mapped to the ids of the rows holding them, and `_store`/`_remove`/`_revalue` -- the only three places in the class that write `_rows`, each under an `RLock` because the circuit dock reads from a worker thread -- keep it current. The rows it finds come back in the order a scan would have found them (an `_order` counter per row) and each is re-checked against the whole `where`, so the answer is exactly the scan's. Still scanned: `OR` selects, NULL-only conditions, a value that cannot be hashed, and an index entry holding over half the table. Cost: the first select on a column builds its index (0.9 ms on 4,500 route rows, 40 ms on 90,000), writes cost about 0.4-1 us more, and each distinct value of an indexed column holds a small set (a few MB for 10,000 wires). Anything that writes `_rows` outside those three methods would silently desynchronise the index. Tested against the previous scan-only class on 106,557 random selects (order included) after random inserts, changes, deletes, mirror calls, deferred deletes and reloads, with five deliberately broken versions of the upkeep all caught, plus a threaded reader/writer run.
