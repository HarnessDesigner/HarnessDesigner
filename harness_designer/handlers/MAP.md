## FILES

#### __init__.py

Package docstring only — explains that most of this package's former `Add*Handler` classes have been migrated onto the objects themselves (see `add_handlers/`) and removed; what remains here is view-agnostic logic those replacements (and `drag_handlers/`/`rotation_handlers/`) still call into: part-compatibility lookups, wire fork/merge, terminal/transition/seal placement geometry, snap-probe building blocks, and the peg-board rope-pull reconciliation solver. No code of its own.

#### bundle_diameter.py

The shared bundle-diameter rule (3D + peg-board) — a bundle's diameter is `max(wire-driven diameter, every attached transition branch's own min_dia)`, and growing/shrinking a branch's own project-level `diameter` to meet the bundle is symmetric (not a one-way ratchet). Wire-driven diameter uses the real concentric-packing figure when one exists, else an "unorganized packing" area-sum estimate scaled by a fudge factor. `wires_diameter(bundle)` is the read-only public form of the wire-driven diameter (mm), used by the circuit solver; unlike `effective_diameter` it never grows a transition branch.

#### bundle_layout_handler.py

Inserts a new interior `BundleLayout` waypoint into a bundle's 3D path at the clicked position/segment (`_create_bundle_layout_on_bundle`), reached only from a bundle's own "Add Layout" context-menu action.

**`remove_waypoint(project, layout_db, view)` (2026-11-08):** takes the waypoint a bundle layout marks out of its bundle's route (`pjt_bundle_paths`, and the routes of the wires through it) and deletes its point, in `'3d'` or `'pegboard'`, then refreshes the owners. Called by both `BundleLayout._delete` views. Before this a deleted bundle layout left the bundle's waypoint behind (route row and point), with nothing to show or delete it. A layout that is not a waypoint of exactly one bundle (an end, a seam between two bundles) is left alone: merging a seam back is not done here.

#### bundle_topology.py

`merge_bundles` — the one bundle-topology operation that survives the waypoint model (bends are just interior waypoints, not forks): merging two independently-placed bundles dragged together end-to-end into one row, mirroring `wire_topology.merge_wires`.

#### bundle_wire_model.py

NEW 2026-10-29. Pure-geometry model (stdlib only, no DB/UI) of ONE wire through ONE bundle: `BundleModel` (ends, fixed length, end directions, guard distance; a guard stub is always DERIVED from its bundle end), `WireModel` (ends, free length beyond the stubs, remembered split), `Assembly.plan(held)` -> `MovePlan` (ordered steps: slide slack through the bundle, pull the opposite end to its stub tip, drag the bundle toward the held end, clamp the held end). Used by `rope_pull_handler._evaluate_points` (`eval_bundle_wire`). Checked offline by `diagnostics/bundle_wire_check.py` (8 scenarios + 5000 random cases, all invariants hold). One bundle per wire only; a chain of assemblies would be the extension for several.

#### concentric_handler.py

Which concentric a bundle / transition branch uses (2026-10-25): `find_concentric_for_bundle` / `find_concentric_for_branch` (read-only, `None` if there is none) and `concentric_for_bundle` / `concentric_for_branch` (the same, making an empty concentric when there is none). A connected bundle and branch share ONE concentric (and so one widget) by LOOKUP, never by writing ids: a bundle uses its own, else the first one among the branches plugged into either end; a branch uses its own, else its bundle's. Where BOTH already have one (made separately before they were joined) each keeps its own -- nothing merges concentrics, so that case still has two widgets. Wires in a concentric (NEW 2026-10-25): `add_wire` (the drop of a wire from a peg-board wire table onto a concentric section widget lands here), `replan`, `needs_plan` and `build_section` (the adapter from the database to `ui/concentric_section`'s `SectionSpec` + `WireDetail`). A wire is "in" a concentric when a `pjt_concentric_wires` row of one of its layers names it; a new wire goes in the OUTERMOST layer, and a concentric with no layers gets layer 0. **Layer diameters are deliberately left alone**: `bundle_diameter._wires_diameter` takes the outermost layer's `diameter` as the bundle's size the moment its concentric has any layer, so a placeholder or a made-up figure would silently resize the bundle in 3D and on the peg board; a new first layer gets the diameter the bundle has right now (its wires' estimate, else the attached branch's `diameter`, else the wire's own OD) and an existing layer's diameter is never rewritten. **`replan` is INTERIM**: it packs every cable as tightly as it can in a circle (`ui/concentric_section/packing.py`) and stores each cable's place in its `point2d`; it does not follow the MIL-STD-339 layer rules (CONCENTRIC_TWIST_DESIGN.md sections 4-8) -- when that solver exists it replaces `replan` and nothing else here changes. It also overwrites every cable's place on each add (a manual drag of a cable is not saved yet either). **Cables are drawn from what the catalog knows** (`_cable_for`): there is no jacket flag and no jacket / shield thickness, so a coaxial or shielded part gets a shield and a jacket (`_SHIELD_FRACTION` / `_JACKET_FRACTION` of its OD), any other wire none (several conductors = a twisted group); the conductor colour is the plating row's own `color`, the insulation / stripe colours the part's. The wire details (`_detail_for`) take the current and temperature from `circuit.solve()` (one solve per circuit per build) and are `None` for a wire in no circuit. Nothing checks that a dropped wire actually runs through the bundle the concentric belongs to. Checked 2026-10-25 against fake rows only (no real database): no duplicates, layer diameters untouched, no overlapping cables, the cable kinds, the details.

#### handler_base.py

`HandlerBase` (~290 lines) — captures mainframe/part_id/camera/ptables state for a handler; mouse-capture lifecycle (`capture_position()`/`release_capture()`/`ignore_next_input()`, where `release_capture` raises `NotImplementedError` so subclasses must implement placement); and orientation-alignment helpers used to snap a newly placed accessory to the face of the housing/cavity it's being dropped into: `obb_face_direction()` (outward-normal for one OBB face), `euler_from_matrix_continuous()` (YXZ Euler from a rotation matrix, unwrapped continuous with the previous angle to avoid +/-180 degree flips), `set_angle_from_housing()`/`set_angle_from_cavity()` (align an object's angle3d to a housing's/cavity's world rotation via `model3d.forward_up` face indices), and `reset_angle()` (reset angle3d to identity).


**Terminal / seal angle in a rotated housing (2026-11-11):** `set_angle_from_cavity` used to return False, writing nothing, when the part's model, its OBB or its forward/up faces were not there yet (a part added before its model loaded, or not oriented), so a terminal added into a cavity of a rotated housing stood at zero rotation. It now falls back to `_mirror_cavity_angle`: the object takes the cavity's Euler angles, matrix and quaternion directly, which is what a housing rotation does to the terminals in its cavities anyway (`PJTHousing._update_angle3d`). Checked on stand-ins only (`twist/cavity_angle_test.py`), not in the app.
#### rope_pull_handler.py

- 2026-10-30: a bundle END sits in its wires' routes, so `_chains_for_point` now returns the bundle first for it (wires follow via `eval_bundle_wire`), and `eval_bundle_wire` re-solves/commits the bundle whenever its ends moved or it still has an overlay. Wire-drag and bundle-drag release run a final non-in_progress reconcile (creates the bend layouts). Pegboard `Bundle._pick_priority = 1` so a wire inside it doesn't win the pick.

The peg-board "rope pull" reconciliation solver (`BUNDLE_PLACEMENT.md` sections 6/6b). `resolve_rigid_move` (interactive drag of an anchor/waypoint) and `realize_length_change`/`realize_3d_move` (after a 3D length change) binary-search the largest fraction of a drag's delta every touched chain can accept, cascading through whatever rigid object (Transition, Housing, Splice, WireServiceLoop) each chain's far end is anchored to when its own slack can't absorb the move. **Cables are chains (2026-11-09):** a placed cable (`PJTCable`) is solved like a wire or a bundle: its two board ends are the anchors, `length_mm` (the 3D route, plane to plane once an end is split) is the length it may have on the board, so the far end is pulled when the near one is dragged too far and the route takes up slack as bends when the ends are closer. It has no layouts, no stubs and no bundle runs: its entries carry `layouts_table=None`, `_is_wire_chain(chain)` is the test for "a wire", `_drop_waypoint` removes a waypoint that left a route (the layout, or for a cable the bare point), `_make_pseudo_layout` answers `None` for a cable and `_set_layout_visible` ignores a missing layouts table. The cable is a rope BETWEEN its two ends; a split end is a group node (see 2026-11-10 below), not the whole cable. A cable's conductor points of an end that is not split are children of the end and are never listed. `_anchor_index`, `_chains_for_point`, `realize_3d_move` and `finalize_drag` include cables. Checked on the real row classes and a scratch SQLite (`twist/cable_rope_test.py`: far end pulled, slack bends written and removed, a drag frame writes no rows), not in the app.

**The cable end group includes the sleeve (2026-11-12):** `_cable_node` adds the three board points of a solder sleeve on that end (`start_/stop_shield_splice_id`) to the end's group; they are the lead's end on the sleeve too, so a pigtail is solved like any other lead. A cable BODY drag in the board uses `resolve_rigid_move` (see `drag_handlers/editor_pegboard/MAP.md`, `cable.py`).

**A drag overlay never outlives an edit of the stored board route (2026-11-09):** the overlay (`_offline_store`) is an in-memory copy of a chain's board route that `_commit_overlay` writes back with `set_route` when the drag releases. An edit of the stored route made in between (above all `Terminal.add_wire` inserting the terminal's and the cavity's wire-side stub points in front of the route while the drag gesture is open) made the copy stale, and the write-back erased the stubs: `_stub_boundary` then found (0, 0), the solver took the wire end (the crimp point, inside the housing) as the anchor and bowed the slack in from there. `_on_stored_route_changed` is registered with `pjt_wire_path.add_route_listener` and drops the chain's overlay and store (showing the markers of the points it had given up) whenever the table reports a `pegboard` (or every-view) change; this module's own commits release the overlay before they write, so they are not affected. A wire whose stubs were already lost (saved that way) has to be attached to its terminal again. The rule the stubs implement: slack is only ever introduced BEYOND the cavity's wire-side point (terminal in a housing) or beyond the terminal's wire-side point (terminal not in one); `_stub_boundary` / `_anchors_and_length` make those the solver's anchors.

**A pulled node never moves a point the user is placing (2026-11-09):** `pull_node` skips a point that is already decided and not a pulled one (`p in fixed and p not in write_points`, i.e. a dragged target). A lead's free end is one of the points of the cable it pulls (`_cable_node`), and the pull used to move it a second time, so a free-ended lead dragged past its length stayed as long as it was dragged (the cable moved by the same amount as the end). `_cable_node` also no longer lists a conductor's end point that belongs to a terminal, splice or loop (`_is_owned_end`): the cable carries only the free ones. A service loop is a rigid two-point node (`[start, stop]`): the pieces of wire either side are ordinary chains anchored on its points, so the length the loop takes in the run is the straight start-to-stop distance of the points, never its coil length (`PJTWireServiceLoop.length_mm`, used only for the circuit totals, weight and resistance). Checked on stand-ins (`twist/lead_drag_test.py`, `twist/loop_chain_test.py`: ends dragged, pieces keep their 3D lengths, the span stays rigid), not in the app.

**Slack, push and the cable as a rope (2026-11-10, user spec):** (1) A chain takes slack up as bends until its ends are `_fold_limit` apart (`zigzag_length_factor` diameters, never more than its length: the spacing a zig-zag needs), i.e. until it would fold over on itself. A near end moved CLOSER than that PUSHES the far end straight away from it to the limit (`_pushed_far_position`, called from `pull_if_needed` after the pull test: pull when too far, push when folded, bends otherwise); the far end is the node that owns it, so the push cascades exactly as a pull does, one chain after another, and a push with nowhere to go makes a chain infeasible, so the resolver stops the move. Only a move that makes the span shorter pushes (the span before is passed as `near_old_xz`): a reconcile that moves nothing, or a chain already closer than its limit, never moves anything. The re-pull branch for a node pulled earlier still only PULLS (no push there). (2) A split end of a cable is a GROUP node (`_cable_node`): the cable's end point, the end's split points and the lead ends that nothing is attached to, translated together; the end point answers the same group. The rest of the cable is not in it: the cable is a chain between its two end points (`required_length` its 3D length), so a pull on a lead goes lead (bends, then pulled) -> end group -> cable (its slack first, then its far end pulled / pushed) -> far end group -> the conductors there, and so on. Before this a lead pull translated the whole cable and its other end, so the cable's own slack was never used. The split points are put back on the trunk's split plane by `Cable.sync_board_split_ends` when the route changes, so a lead ends up a little off its solved length (by the plane's turn times the trunk's half width) until its own slack handler re-fits it; not corrected. (3) A wire service loop is its own node kind `'loop'`: pulled through one point it puts the other point straight on from the near end of the pulling chain at its own span (`pull_node(..., inline_from=near end)`), so it stays in line with the wire (a pull or a push alike); without `inline_from` (the bundle-wire path) it translates. A splice stays rigid. (4) `realize_length_change` for a plain wire or a cable keeps the END THE USER MOVES where it is (the slack handler passes the moved point, `held_point_id`) and pulls / pushes the other; before, the start always stayed and the stop was pulled back, so dragging a stop end clipped instead of pulling its far side. Checked on stand-ins (`twist/cable_cascade_test.py`: lead used up, cable slack used, far end pulled, lead folded -> pushed, cable folded -> far conductors pushed, a no-op pushes nothing; `twist/loop_inline_test.py`; `cable_rope_test`, `loop_chain_test`, `lead_drag_test`, `wire_stub_test`), not in the app. Not done: the fold limit is `zigzag_length_factor` diameters (the solver's own spacing), not a bend-radius rule; a push into a transition pivots it like a pull does.

**Trace (2026-11-10):** `Config.editor_pegboard.rope_pull.trace` (off by default; a drag runs the solver many times a frame) writes one `[rope]` log line per decision: `solve` (the dragged points and where they go), each `far end` decision (span, the chain's length, the fold limit, the result: pulled / pushed / unchanged), each `pull node` (kind -- `rigid`, `loop`, `transition` --, its points, the move, `inline_from`), each chain (`wire` / `lead ... of conductor` / `cable` / `bundle`, which end was dragged, the near target, bends written), `REFUSED` with the chain that could not be satisfied, `done` with every point that moved, `commit`, `drag resolved` (the fraction of the drag that was reachable) and `realize` (which end of a reconciled wire is held). Ids are the 4 middle bytes in hex (`_short`). Helpers: `_trace`, `_label`, `_short`, `_xz`.

**Cost of a solve (2026-11-10, from a trace of a hang):** dragging a housing of a project with a nine-conductor cable (loops in its leads) ran 152 solves in 30 s; 68 were refused only after 100-170 node pulls (the move was more than the leads allow), and `resolve_rigid_move` runs one solve per halving of its binary search, so one drag frame cost seconds and the application looked hung. (1) `_MAX_PULLS_PER_SOLVE` (120; the largest feasible solve seen used 66) refuses a solve that has pulled that often. (2) `resolve_rigid_move` halves 16 times, not 32 (1/65000 of the drag). (3) `_trace` takes a function that makes the parts of the line, so a solve that is not traced builds none of the text (the first trace patch built every line's text whether tracing or not). Whether the refused solves are a real limit (the leads of a cable cannot all reach) or a ping-pong between the pulls of a loop and its neighbours is not settled: a stand-in cable with loops in its leads (`twist/loop_osc_test.py`) converges, inline or rigid; the project in the log was not reproduced.

**A drag that could not move at all (2026-11-11, second trace):** dragging a housing resolved to fraction 0.0, `feasible=False`, and every frame ran the whole refused cascade 16 times. The saved state was not feasible to begin with: the leads of a cable's end were 1.2-1.6 mm over their length (the split points are laid on the trunk's plane), so the leads, all taut in different directions and all ending in one rigid object (a housing's terminals), pulled that object over and over, each pull breaking the previous one (alternating projections onto touching circles never settle), until the pull budget ended the solve. Two changes: (1) `tolerate_stretch` (`_evaluate_points`, `realize_length_change`; `resolve_rigid_move` and the slack handler's safety net pass it): a chain already further apart than its length is taut at the span it has, so only stretching it more pulls; a change of a wire's own 3D length (what `realize_length_change` is for) still pulls the whole stretch out. (2) A node pulled AGAIN in a solve is carried by what the near end moved (`pull_if_needed`, `entry_far_xz + near delta`) when that keeps this chain within its length, instead of the straight pull toward the near end: the near ends are points of one rigid group, so every chain stays as it was after one carry. On a stand-in (two taut leads of different directions from a cable's end to a splice, one stretched) a drag at the far side took 45 pulls before, 8 now, and the splice is carried as one piece (`twist/taut_group_test.py`). The stretched leads are not shortened by this; they stay as they were. The hang watchdog file stayed empty: the application was slow, not blocked.

**Leads pinned to a housing have no 3D length on the board (2026-11-11, user design):** the board does not share the 3D view's positions, so where the conductors of a cable (or the wires of a bundle) come together can be anywhere relative to the housing they plug into, and the length of each wire there cannot be its 3D length. For each end of a cable and each HOUSING its leads plug into (`_housing_id_of`: the lead's free end is a terminal seated in a cavity), the LONGEST of those leads is the most any of them may be on the board (`_pinned_info`): the length of its wires (without the terminal / cavity stubs, `_anchors_and_length`) plus the coil length of each wire service loop in it (`PJTWireServiceLoop.length_mm`; a loop is not drawn on the board). A lead is followed from the cable's split point over its wires and loops (`_lead_pieces`); a lead's wires share its cap in proportion to their own lengths. A pinned wire has NO slack: `_evaluate_points` takes the cap as its length (`_pinned_cap`), never pushes its far end (`min_span` 0), and solves it as the straight line between its ends (`required_length = min(cap, span)`, so the committed interior has no bend); only a span OVER the cap pulls (the cable end group, then the cable...). A shorter lead is therefore straight and may be longer on the board than in 3D, up to the cap. A lead whose free end is not in a housing, the cable's own trunk and wires that are not cable leads keep the 3D length rule. The loops of a pinned lead are one point on the board (`pull_node`: span 0). Checked on stand-ins (`twist/pinned_lead_test.py`: all caps equal the lead with the loop, straight leads shorter in 3D than the board span, pull only past the cap), not in the app. **Not done: wires routed through a BUNDLE** (`eval_bundle_wire` / `bundle_wire_model.py`, the stub + bundle + stub + free length model with its slide-slack rule) still keep their 3D length per stretch; the same rule (cap = the longest wire of the bundle end and housing, straight) has to be built into that model.

**Pinned wires are straightened after the load (2026-11-11):** `straighten_pinned_leads(mainframe)` (called by `Project.__init__` after the objects are built, in one gesture) re-solves every wire of a pinned lead that has route points beyond its terminal / cavity stubs (`realize_length_change(..., tolerate_stretch=True)`): they come out straight. A project saved before the pinned rule, or after a drag that went wrong, kept bends nothing re-solved until the housing was next dragged. A wire over its cap (a housing separated from its terminals) is left as long as it is, not pulled in. `finalize_drag` also passes `tolerate_stretch` now. The terminal and cavity stub points of a wire stay: they are the straight run out of the terminal, so a pinned wire is stub - straight line - stub, with a corner at each stub tip.


**How a pinned lead is measured (user, 2026-11-11):** what is inside the housing is fixed and moves only with the housing; the length that counts, and that the rope pull works on, runs from the BACK OF THE CAVITY (`PJTCavity.wire_position`, the second stub, after the terminal's own stub) to the cable end (the conductor's split point). `_anchors_and_length` already does this for a wire: the stub points (`_structural_stub_ids` / `_stub_boundary`) are not part of the solve and the 3D length of the stub segments (attach -> terminal stub -> cavity stub) is taken off `length_mm`. `_pinned_info` adds the straightened-out `length_mm` of every wire service loop in the lead (the coil's wire length, not drawn on the board) to the lead's wires. Checked on the data of project 5 (`twist/measure_check.py` on a copy of the DB): the stub segments are 19.7 mm in both views and the free length of each wire is equal in both. **Older projects (1, 3, 4) have board routes whose first points are not the terminal's / cavity's stub points** (cloned without `parent_point_id`, or at other places), so `_stub_boundary` finds no stubs there and the part inside the housing counts as free wire; `_stub_boundary` now logs one warning per such wire. Use a fresh project (the data of those is not repaired).

**Loops of a pinned lead stay on its straight line (2026-11-11):** a loop only moved when a piece beside it had to pull it, so a housing or a cable moved SIDEWAYS left the loop where it was and the lead bent there (the bend 'where the loops would be' on the board). `_pinned_info` now also lists the leads that have loops (`'leads'`: pieces, their caps, loops, split point, terminal end), and `_evaluate_points` runs `place_pinned_loops` after the pending points are processed (up to 3 rounds): the loop of each touched lead goes to its share (the pieces' caps counted from the split point) of the straight line from the housing's effective end to the split point, both of its board points at once, the pieces beside it are forgotten (`seen_chains` / `entries`) and solved again from there. Checked on stand-ins (`twist/pinned_lead_test.py`: housing moved sideways, loop collinear at 0.455 of the lead), not in the app.

⚠ That cross-check missed a real bug, found + fixed 2026-10-27 on the feature's first live end-to-end run: `RouteWalk.__init__`/`_advance`/`choose` built `self._ordered`/`self._point_tags` from THREE different id sources, two of them wrong. `branch.position3d_id`/`transition.position3d_id`/`pjt_bundle_paths_table.point_ids(...)` (table-column reads) correctly give the raw 16-byte `pjt_points3d`/`pjt_points_pegboard` row id. ⚠ Second bug, same first live run, same `_commit_route` (found + fixed 2026-10-27, user report): the two guard `WireLayout`s it creates rendered with the wrong diameter AND color — always `WireLayout.__init__`'s own hardcoded fallback (3.0mm, plain gray plastic), never the actual wire's part. The live in-drag teleport-onto-a-probe already works for peg-board (via `SnapProbeSet`'s peg-board subclass); only finalizing that specific case into a real connection on mouse-up does not yet.

2026-10-30: `snap_point` for a SEATED terminal returns its cavity's `wire_position3d` (wire-side surface), not the terminal's own buried point. **Leads of a cable's conductors (2026-11-08):** the free end of a lead snaps and commits as any wire end does (a seated terminal snaps at its cavity's wire-side surface). Two things that stopped it: `_awg_fits` compared the wire's AWG without checking for `None` (a cable's conductor can have no AWG of its own: a `TypeError` while the probe set was built, so the drag never armed), and `commit_snap` deleted the lead's old end point once no wire used it, though the lead's CONDUCTOR row still points at it (the cable reads it when it is built). A lead's end point is now kept. Not run in the app.

**Solder sleeve (2026-11-11, `SHIELD_SLEEVE_DESIGN.md`):** `check_splice_compat` refuses a wire on a solder sleeve that already has a wire on its branch point (its pigtail, whether it came with the sleeve or the user snapped it on): 'This solder sleeve already has a pigtail'; with none, the sleeve is a snap point whatever its catalog type. `wire_drag_base.is_anchor_point` treats the branch point of a cable's solder sleeve as an anchor (3D only), so the end of the pigtail set onto the sleeve is not moved by a drag. Every editor's snap and add-wire path goes through this function.

**Pigtail the user adds (user, 2026-11-11):** `check_splice_compat` also refuses a wire on a sleeve WITHOUT a pigtail when the cable it is on (`_sleeve_cable_diameter`: the `pjt_cables` row whose `start_/stop_shield_splice_id` is the sleeve) and the wire together do not fit (`Splice.fits_pigtail(cable od, wire od_mm)`); a sleeve on no cable is not asked. No length limit for such a pigtail. The pigtail of a CATALOG sleeve (`has_pigtail`) is limited to 150 mm from the middle of the sleeve: `WireDragMixin._apply_budget_clamp` now calls `_clamp_sleeve_pigtail` (3D points table only), which shortens a drag that would make the route (sleeve end, bends, dragged end) longer than that and lets one that does not lengthen it through. Stand-in test `twist/sleeve_shielding_test.py`; NOT run in the app.

#### wire_topology.py

`split_wire_at_point`/`merge_wires` — forking a wire in two around a real junction (splice, wire service loop) and merging two forked wires back into one when the junction is removed. Ordinary bends never go through here (see `wire_layout_handler.py`). Two merges, same result, different method: `merge_wires` makes a NEW wire row spanning `wire_before`'s start to `wire_after`'s stop (new ids; its route rows are re-created by `set_route`, so bundle/transition tags on them are lost) and deletes both originals; `merge_wires_in_place` (2026-10-26, wire service loop delete) keeps `wire_before`'s row and object, repoints its stop ids in every view to `wire_after`'s far end (`obj3d`/`objpegboard`/`objschematic.set_stop_position`), moves `wire_after`'s route rows onto it by changing each row's `wire_id`/`idx` (tags stay), moves its markers and far-end sibling, deletes the emptied `wire_after`, and deletes NO point row (the two points the wires met at just stop being used). **Both take the wires in running order: `wire_before` is the one whose STOP is at the junction, `wire_after` the one whose START is** -- a caller that goes by a junction object's `start_sibling`/`stop_sibling` must not pass them straight through (for a wire service loop `start_sibling` is the wire AFTER it). `Splice.delete` and `WireLayout._reconnect_wires` still call `merge_wires`. `add_handlers.editor_3d.wire_service_loop.restore_wire_from_split` (the cancel-placement path) now calls `merge_wires_in_place(state.wire2, state.wire1)` (`wire2` is the wire BEFORE the loop, `wire1` the one after it) and no longer deletes the two wires again afterwards (it used to pass them to `merge_wires` in the wrong order and then delete both, already deleted by the merge).

**Cable leads (2026-11-09):** `split_wire_at_point` gives BOTH halves the wire's `cable_conductor_id`, and `merge_wires` the merged row the id of either half, so a splice or a wire service loop in the lead of a cable's conductor leaves every piece that conductor's wire (its part, so colour, size and resistance, resolve through the id). The lead proper is the piece whose stop is the conductor's split point: it is the one `CableConductor.replace_wire` hands the junction to (the split moves the stop sibling to the half that keeps the stop); the pieces beyond the splice or loop have no junction. A `merge_wires_in_place` keeps the surviving row's id (both carry it). **Board geometry (2026-11-09):** a wire that has peg-board end points is cut on the board too, at the same fraction of its route length as the 3D cut (`_split_board`): both halves share a new board point there, the board waypoints are divided like the 3D ones (those before the cut segment go to the first half) and each half gets its end ids. Before, the halves had none, and a missing end is created lazily at the board's origin (`start_position_pegboard_id`), so the pieces of a split lead (and of any wire with a splice or loop) were zero-length wires at (0, 0) and not seen on the board. `merge_wires` joins the board ends and waypoints of the halves again. A wire with no board geometry is split as before. `split_wire_at_point`, `merge_wires` and `merge_wires_in_place` end by telling the peg-board wire table of each housing a terminal on the new wire's ends is seated in (`_refresh_housing_tables`, via `notify_table_wires_changed`): the table bakes in its wire ids, and the wire that was split or merged is a row that is gone (picking it in the table raised `IndexError`). Bundle tables are not told. A splice's own board points are NOT set from the cuts (only a loop's, in `objects_3d/wire_service_loop.py` `start_add`). Checked on the real row classes with a stand-in `Wire` facade (`twist/lead_split_test.py`), not in the app.

#### Wire-snap probes (built 2026-08-05/06)
Invisible-sphere snapping so a wire snaps onto a free-standing terminal's back point, a cavity's wire-side point (terminal seated inside a housing), a splice's branch point, or another dangling same-part wire end, without a pixel-precise hit. Used by `wire_handler.AddWireHandler` (two-click) and the 3D/peg-board endpoint/path drags.
- **Probes:** `database/project_db/pseudo_wire_layout.py`'s `PseudoPJTWireLayout` is a real `PJTWireLayout` subclass (type checks need the real type) that never touches a row. `wire_snap.py`'s `SnapProbeSet` builds one set per session and reuses `objects.wire_layout.WireLayout` as the pick target. Construction is two-step (`PseudoPJTWireLayout(None, uuid)` then `.configure(...)`) because the `_PJTEntrySingleton` metaclass fixes `__call__` to `(table, db_id)`. Tag probes via `configure()`'s `terminal`/`wire`+`end`/`splice` so `resolve_picked`/`get_snap_info` can unwrap a hit. Never call `.delete()` on a probe's `WireLayout` (it runs `_reconnect_wires()`); `SnapProbeSet.close()` uses `mainframe.remove_object()`.
- **Snap point:** a free terminal's `wire_position3d` (back-face centre); `attach_position3d` (the crimp point) is buried and never a snap point. A cavity-seated terminal snaps at the cavity's `wire_position3d`. The probe position is only a visual target; `Terminal.add_wire()` always uses `attach_position3d` as the wire's real endpoint.
- **Pickable but invisible:** `ArrayPool.hit_test(visible_only=True)` only tests slots marked visible this frame, and `BaseVar.render()` marks them after its `is_visible` early-exit. A probe is `is_visible3d == False`, so `PJTWireLayout.is_snap_probe` (True on `PseudoPJTWireLayout`) makes `BaseVar.render()` call `mark_visible` without drawing. Any new invisible-but-pickable marker needs the same flag; a registered OBB/AABB alone is not enough. Probes get a pick diameter floor `_SNAP_PROBE_MIN_DIAMETER = 10.0` (`objects/objects_3d/wire_layout.py`). The bundle/transition snap bypasses `find_object` entirely (own ray + fixed 5.0 mm radius math).
- **Shared points (`parent_point_id`):** the second and later wires on one terminal get their own `pjt_point*` row (a row belongs to one wire's waypoint list) that tracks the first wire's point. The column exists on all three `pjt_points3d/2d/peg` tables. Do not call these "clones" (that word means the `_is_clone`/`Point.attach()` preview alias). Schema changes go in both `harness_designer/database/create_database/` and the sibling `harness_designer_database` repo (they already drift; do not "fix" that while adding a column). Propagation is deliberately split by volume: housing move/rotate uses one batched `_find_child_points()` query folded into the housing cascade's direct-numpy `batch_update` (no per-point callbacks); everything else uses `Point.bind()` (`PJTPoint3D._sync_from_parent`), since a parent has only a handful of children. If a new "tracks a parent" need appears, ask which regime it is in.
- **Compatibility warnings:** only the upper bound of a terminal's/splice's combined cross-section is checked. Exceeding it never blocks, including AWG crimp-range mismatches during a drag (red `SnapOverlay` for a block message, amber for a capacity warning); only the two-click flow keeps its confirmation dialog for a hard AWG mismatch. A splice has two crimp locations: count only one of `start_sibling`/`stop_sibling` plus every `branch_wire`. Only single-crimp splices are modelled; "bus type" splices come later, do not build toward them unasked.
- **Process:** this took 3-4 attempts; asking precise clarifying questions is what finally got it right, so do that for similar foundational changes.

#### Wire-into-skeleton drag (BUNDLE_PLACEMENT.md section 12), lasting rules (built 2026-10-03, debugged 2026-10-08 to 10-29)
Dragging an existing wire's interior section (strictly between two of its own waypoints, never touching its true start/stop) onto a bundle free end or transition free branch routes the wire in. `wire_routing_drag.py` (`begin_route`, `RouteSession`), `wire_routing_handler.py` (`RouteWalk`, `_commit_route`), `rope_pull_handler.py`.
- **Peg-board middle drag:** a wire's peg-board waypoints are independent of its 3D ones and usually absent. With none, the body is one segment, and if one end is anchored a click anywhere moves the free end (both anchored: nothing drags). This is by design, not a picking bug; add peg-board handles ("Add Layout" in the peg-board view) first.
- **`Point.db_id` has a 2-byte view suffix** (`b'3d'`/`b'2d'`). Slice `[:-2]` before using it as a `pjt_points*` row id (table reads such as `position3d_id` are already raw). Both are plain `bytes`, so nothing type-checks the mix.
- **`WireLayout` snapshots diameter and colour once** at construction (from `attached_wires`, falling back to 3.0 mm / grey). Create a waypoint's `WireLayout` only after its route row exists (`set_route` first).
- **Cross-view:** 3D governs, peg-board conforms. After the primary commit `_route_companion_view` builds a second `RouteWalk` for the other view from the stored `entry` and `_hops` (keep both alive until it runs), then reconciles length. `EndAtSplice` is refused (splices are not wired into this feature; its `point_id` is view-specific). The companion splice index comes from `wire_topology.segment_index` on the entry's position in that view, never from correlating waypoint indices. `RouteWalk` clamps `_section_idx` to `[leading, interior - trailing]` for peg-board so the splice cannot push a terminal/cavity stub off the list end (`_stub_boundary` identifies stubs purely by position).
- **Protected points (`rope_pull_handler`):** points tagged `bundle_id`/`transition_id`/`transition_branch_id`, plus their guard stubs, are fixed to the wire's own solve (`_wire_protected_runs`, `_reconcile_wire_through_bundle`; free segments are solved separately, paired by order across views). A bundle's own interior waypoints are removable only by the bundle's solve, which always runs first (`realize_bundle_and_wires`; `_resync_wire_bundle_span` re-syncs wires when the bundle's waypoint count changes). A plugged-in bundle end shares the transition branch's literal point row, with no separate guard. Any code that rewrites a wire's peg-board interior must go through `_reconcile_interior`; a direct `set_route` reintroduces the bug where the bundle segment was swept into disposable slack. `PJTWirePathsTable.set_route` drops all tags, so callers restore them. Never hand-write `idx`.
- **Wire model:** stub + bundle + stub + extra free length at each end. A drag slides slack through the bundle, then pulls bundle and wire (shared free length with a remembered split, `_wire_gap_split`). The bundle-routed wire's guard stub keeps its length and the bundle's end direction; wire drags never move bundle/guard points (`wire_drag_base._route_locked_point_ids`). Bundle-routed wires bypass the overlay path (`_apply_mid_drag`/`_place_active`/`_commit_overlay`) because it drops tags. An infeasible peg-board fit pulls the wire's own ends (`_evaluate_points`, `pull_if_needed`). Taut pulls need `_STRETCH_TOLERANCE_MM` (float32 storage).
- **Table refresh:** after routing into a bundle call `base_pegboard.notify_table_wires_changed(bundle_db)`; transition tables need the same and do not have it yet.
- **Open / unverified:** bundle selection after routing; `_commit_overlay` still drops tags; a wire with a terminal stub plus a bundle, two bundles on one wire, a bare transition pass-through and the multi-transition `RouteSession` path have not been exercised live. Only the single-bundle case is confirmed.

#### Wire merge extends the existing wire; it never creates a new one (user, 2026-10-23)
`WireDragMixin.merge_wire_into(project, wire_obj, other_wire, other_end, own_end)` ([handlers/wire_drag_base.py](harness_designer/handlers/wire_drag_base.py)) absorbs the preview/dragged wire into `other_wire` and returns `other_wire`, following `Terminal.add_wire`'s vocabulary: the old end point becomes an interior waypoint, `wire_obj`'s waypoints follow seam-outward, `other_end` takes `wire_obj`'s far end in 3D/peg board/schematic, the sibling moves over (`set_sibling` + `replace_wire`), `wire_obj` is deleted and `on_wire_attached` re-routes the schematic. Peg board is touched only when both wires have full peg-board geometry. The add-wire handler (`add_handlers/editor_3d/wire.py`) sets `_finalized = True` BEFORE merging, otherwise the handler's `delete()` takes the cancel path and deletes the preview wire a second time (`RowDeletedError`). If unexplained errors return (`wire_slack_handler._reconcile` KeyError on a deleted wire, `end_gesture()` with no gesture open, a pegboard `_on_wire_selected` IndexError), re-add logging at `_arm`/`begin_gesture`/`end_gesture` first.
