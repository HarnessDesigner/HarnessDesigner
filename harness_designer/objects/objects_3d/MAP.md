#### cable.py

`Cable(Wire)` (NEW 2026-11-05): the 3D view of a placed cable. A SUBCLASS of the 3D wire view, so the trunk is drawn exactly as a wire is (path, mitred bends, and the twisted conductors of a part that `is_twisted`); a ribbon cable is a plain round tube until the flat strip is built. Differences: `refresh_waypoints` skips the peg-board slack handler (a cable has none), `handle_interaction` forwards only to the placement session and otherwise returns `False` (so a click selects; dragging a placed cable's end or waypoint is not built, the wire's drag plans assume a wire), `get_context_menu` returns `CableMenu` (Select and Delete only), and `start_add_cable(mainframe, canvas, part_id)` builds the cable at placeholder points and arms `add_handlers.editor_3d.cable.Cable`. The crimp-end look never shows because the facade's siblings are always `None`. **Split ends (step 5a, 2026-11-05):** `_start_split` / `_stop_split` (cached from the row by `reload_splits`) make `_segments` start / end the trunk at the split planes (inside the first / last segment only), `_build_slots` makes one `_Slot` per conductor row (its place in the cable from `shapes.twisted_wire.profile`, and where its end lands when fanned out; a shield sits at the bottom of the jacket), `_lead_frames` gives the trunk axis, frame and helix angle at each plane, `split_positions(start)` the conductors' places on the plane (turned by the twist, so a lead meets its conductor without a jump) and `fan_out_positions(start)` the fanned end positions. The leads themselves are ordinary wires (see `objects/MAP.md`), drawn by `objects_3d/wire.py`; the 5a drawing of leads inside this view is gone. The menu offers "Split Conductors (start|stop end)" (a distance dialog) or "Join Conductors" for the end nearer the right click. "Join Conductors" is enabled only while `can_join`. **Fan-out order (2026-11-06):** `fan_out_positions(start)` keeps one fixed place per conductor row around the end (its spot in the cable, spread out) and gives each conductor the place numbered by its `start_order` / `stop_order` (an order that is not a permutation is ignored); the menu's "Fan-out Order (start|stop end)..." opens `ui/dialogs/fan_out_order.py` and is enabled with 2+ conductors while `can_reorder`. **Not run in the app.** **Step 4, trunk by style (2026-11-06):** the view picks its look from the part: twisted as the wire view draws it; RIBBON (`_build_ribbon`, `_ribbon`) a row of touching round conductors (`shapes.twisted_wire.ribbon_profile`) through the same shader at rate 0, colours from the part's conductor rows (the cable's colour when it has none); JACKETED one plain tube at `trunk_size`. A ribbon's `_segment_transforms` yields each segment's angle already turned about its direction by the roll of the flat side (`roll_deg` at the start, parallel-transported round bends; cached in `_rolled`, cleared by `_recalculate_geometry`) and a scale of (width, thickness, length), so the strip's own box is what picking and the selection overlay use and the shader needs no phase; `_roll_segments`. Menu: "Roll Ribbon..." (ribbons only, enabled while neither end is split: the split points sit on the flat side) and "Fan-out Order" is disabled for a ribbon (pin order). Slots / fan places of a ribbon come from the row, so the fan-out is across the width. Not built: the web between conductors, a warning for an in-plane turn (a ribbon bent edgewise just stretches its outer edge on screen), a default roll that lies the ribbon flat (it is the 3D view's own frame, roll 0), laminated FFC / FPC. **Not run in the app.** **Step 7:** the conductors' colours and stripes are the catalog part's (`part.conductor_colors`, the `wire_conductors` rows: an edit in the part's Conductors tab is global); the shield is not drawn in the trunk. `reload_look()` rebuilds the look (and the slots) after such an edit (`Cable.reload_looks`, from `Project.reload_cable_looks`). **Step 8 (2026-11-06):** `CableMenu` has `_has_roll` and `_click_world()` so the peg board's menu (`objects_pegboard/cable.py`) is this one without the roll; the peg-board view is seeded from this route. **Drag (2026-11-07):** `handle_interaction` now starts `drag_handlers/editor_3d/cable.py` on a left-down on the selected cable (MOVE / LEFT_UP as the wire view's); the placement session is checked first.

#### wire.py

**Cable leads (2026-11-06):** a lead's waypoints are the wire's own (`WireMenu` Add Handle -> `WireLayout`, 3D route only: a lead has no peg-board or schematic route). `WireMenu` disables Add Splice, Add Wire, Add Wire Service Loop and Add to Wire on a lead (`_NOT_ON_A_LEAD`): each would split or branch the row into a wire with no conductor. Its split end is a drag anchor (`handlers/wire_drag_base.py`). **Not run in the app.** Part of the wire family (with `wire_layout.py`/`wire_marker.py`/`wire_service_loop.py`). `Wire` has hooks a cable view overrides (2026-11-06): `_trunk_size(part)` (width, thickness; a wire is round at `od_mm`), `_make_look(diameter)` (the twist look or None), `_conductor_materials`, `_segment_joins`; `_segment_transforms` scales by `_scale.x` x `_scale.y` (equal for a wire). `reload_conductor_colors()` redraws a LEAD in its conductor's colour and stripe colour after an edit (colour only: a stripe added or removed, or a changed diameter, needs the wire made again).

`segment_obbs()` is the public per-section box a collision test needs: `(S, 8, 3)`, one oriented box per wire section in the bounds pool's corner order (0 = min corner, 1 toggles x, 3 toggles y, 4 toggles z). **A wire's pool OBB (`obb`, from `_compute_obb`) is NOT that**: it is the axis-aligned union envelope of every section, so a diagonal or bent wire's `obb` is a far larger box than the wire — fine for picking, wrong for collision. `_segment_world_corners` (the min/max source for `obb` and `aabb`) reuses `segment_obbs`. `ray_trace_parts()` yields what `render()` draws for `ray_tracing.scene.Scene.add_object`: a `(position, angle, scale, material)` per tube (crimp ends at the conductor diameter/material), and after each non-crimp tube -- unless the wire is selected -- the stripe as `(position, angle, scale, material, (start, stop), vbo)`, the same offsets `render()` passes to `render_segment`. `WireStripe.ray_trace_parts()` yields nothing so a stripe that is also in the visible-object list is not added twice. **Twisted pair / triple (NEW 2026-11-05, `TWISTED_WIRE_DESIGN.md`):** a wire whose part `is_twisted` builds a `_TwistLook` (`_build_twist`) and `render()` hands over to `_render_twisted`, which draws one tube per conductor per path segment through the faces program's twist mode (`shapes/twisted_wire.py`), each in its conductor's colour and stripe, or all in the selection colour when selected. The per-segment phase / mitre / ring counts (`_twist_segments`) are cached in `_twist_plan` and thrown away by `_recalculate_geometry`. Not done for a twisted wire: the debug edge / normal / vertex passes, the bare-conductor look at a crimp end, a wire stripe, and `ray_trace_parts` (still the plain tube, in the jacket colour, which is "no colour"). Picking, the OBB / AABB and the selected overlay still use the plain tube at the cable's OD. **Rounded bends (2026-11-07):** `_twist_segments` runs a twisted cable's segments through `shapes.twisted_wire.round_bends` before `plan`, so a waypoint is drawn as an arc of short chords (radius 4 cable diameters), not a rigid mitred corner; the straight segments from `_segment_transforms` (picking, OBBs, `segment_obbs`, the selected overlay, `Cable._lead_frames`' first/last segment) are NOT rounded, so near a sharp waypoint they cut the corner the drawn arc rounds off. A ribbon (rate 0) is not rounded.

#### wire_service_loop.py

Part of the wire family. The 3D loop view; its placement collision avoidance (`_resolve_collision`: the nearest clear roll about the WIRE in 2 degree steps, then slide along the wire up to the two wire points and any marker) is the part with history. **The loop rolls about the wire, not about the line between its own start and stop points** (user, 2026-10-25): that line sits at an angle to the coil's axis (the helix's connection vector is 27.2 degrees off the wire direction, the stop point 2.8 mm off the wire line), so rolling about it makes the coil wobble. `_wire_points` finds the wire point just before the loop (previous point of the attached wire that ends at the loop's STOP point: a waypoint or its start) and the one just after it (next point of the attached wire that starts at the loop's START point) -- the stop point is the one on the side the wire comes from, the helix's endpoint lies behind its start, and `split_wire_for_loop` leaves the wires that way (checked against saved projects); `_wire_pivot` makes the axle their line and the pivot the point where it meets the start/stop line (the start point, which is on the wire); `_implied_stop` is the stop point the mesh implies (`_p2` can be stale mid-move). A roll is a rigid rotation about the axle through the pivot of the mesh AND the start/stop points; **the object turns about its OWN origin, so the angle handed back is the roll composed AFTER the current angle (`q_roll (x) q0`, Q·R0), together with the new start point** — the old code's `q0 (x) q_roll` twisted the mesh about a vector in its own frame and dragged the stop point 1.7-6.6 mm off the wire (up to 14.7 mm of mesh error at large angles). With no wire on both sides (a project still loading its wires) there is nothing to roll about and `_resolve_collision` does nothing. **Rotate on Wire (user, 2026-10-25):** the context menu's "Rotate on Wire" (disabled without `can_roll_on_wire`) calls `start_wire_roll`, which selects the loop and arms `rotation_handlers.rotation_rings.WireRollRings` as its `_active_handler` and the canvas's `active_handler_obj`. `WireRoll` freezes the loop's pose (`begin_wire_roll`: axle and pivot from `_wire_points`/`_wire_pivot`, the angle's matrix, the start point) and `pose(degrees)` is the rigid roll from it (`R' = Q R0`, start carried round the pivot); `roll_to` writes it through `_apply_resolved` and re-derives the stop point. No collision search runs on it: the roll the user drags is the roll the loop gets. **Lock to Wire (user, 2026-10-25):** a checkable context-menu entry (`lock_to_wire`, not saved; off after a reload) makes `_create_drag_handler` return `drag_handlers/editor_3d/wire_service_loop.py`'s handler, which calls `slide_along_wire(distance)`. With `gap` = half the loop's length along the wire (`abs(dot(stop - start, axle))`, ~3.25 mm for a 3 mm wire): the loop slides until its leading end is `gap` from the next point of the wire, then `_hop`s that point if it may, else stops. `_hop` needs a waypoint (not the wire's end), not tagged to a bundle/transition (`PJTWirePath.bundle_id`/`transition_id`), on no other wire's route, `_corner_is_free` (the matching `WireLayout.can_drag()`, which is False for a waypoint that is a cavity's, terminal's or splice's own point or a wire guard; no layout at all counts as not free), not a U-turn, and a next stretch of at least `3 * gap + length`. It turns the loop about the waypoint by the bend (the minimal rotation, so the roll relative to the wire is kept), sets it down with its trailing end `2 * gap` past the waypoint (leading end `2 * gap` short of it going backward; `2 *` so a tiny step back does not hop straight back), moves the waypoint between the two wires' `'3d'` routes (`pjt_wire_paths_table.remove`/`append`/`add`, then `refresh_waypoints()` on both; the 2D and peg-board routes are left alone, each view's waypoints being independent) and rebinds every marker on either wire (`rebind_wire`). **Markers** are passed, not obstacles, while locked: a marker rides its wire at a fixed fraction of the stretch between two points, never closer to either than `WireMarker.end_buffer`, so one the loop closes in on is pushed ahead of it; within `end_buffer + gap` of the loop's end it is handed to the wire on the other side (`_pass_markers`), set down at its end buffer from the loop. A marker on another stretch of the wire is ignored. The slide itself writes through `_apply_resolved` (the loop's `_update_position` unbound), so `_resolve_collision` does not run during it. The ordinary three-axis gizmo still turns the loop about its CENTROID (`centroid` property; `_update_angle`), and its rings are centered on that centroid, not on `position` -- see `rotation_handlers/editor_3d/MAP.md`. `begin_move_session` (called by the add handler and the drag/rotate handlers, paired with `end_move_session`) gathers every candidate — visible wires other than the two attached ones, other loops, markers on the attached wires — as boxes (a wire is one box per section via `Wire.segment_obbs`, tagged `KIND_CYLINDER` because a section's mesh is a cylinder; anything else its pool `obb`, tagged `KIND_BOX`) and builds ONE `wire_service_loop_search.LoopSearch` from them plus the loop's own mesh (`self._vbo.vertices`, the first `vertex_count * 3` floats of the packed data); `_resolve_collision` only works out the axle, pivot and slide limits and applies what `LoopSearch.search` returns (the new angle and start point). Reached outside a session (the `__init__` call) it builds a one-shot session. **Do not put a pose test back in Python**: adding a loop used to freeze the app (mesh-vs-mesh test, ~6 s per overlapping pose, then ~610 us per pose in numpy because `Angle.from_quat` alone is ~240 us); see this file's DESIGN NOTES's "Adding a wire service loop froze the app". **The loop's Euler is kept in step with every quaternion-only write (user, 2026-10-26):** `_write_angle` copies its target's CACHED Euler, and an `Angle` built by `from_quat`/`from_matrix` has none (`as_euler_float` is `(nan, nan, nan)`), so a "Rotate on Wire" roll, a collision roll, a Lock to Wire hop and `set_placement` all wrote NaN into the loop's Euler while its quaternion and matrix stayed exact; the loop drew correctly, but the ordinary right-click gizmo (planned from Euler) showed only its Y ring, whose protractor was incomplete. Every caller now builds its target with `_angle_from_quat`, which reads the Euler off the loop's FRAME with `_frame_euler` (the columns of the rotation matrix: right = local +X, the coil's axis, the side the doughnut hole is seen from; top = +Y, the loop's diameter; front = +Z, the two straight leads; read from `shapes/cylinder_helix.create_vbo` and confirmed with the user from rendered views) and seeds it with the Euler the loop already has, which picks between the two Euler triples of an orientation and, with the front straight up or down (a loop in a vertical wire, where yaw and roll turn about the same line), holds the roll. **`Quaternion.as_euler` is deliberately not used** (user: gimbal lock only appears converting TO Euler, so Euler is only ever taken from a cache or read off the known frame). **`start_add` sibling ends (2026-10-26):** after `split_wire_for_loop`, `state.wire1` is the wire AFTER the loop (starts at the loop's start point, keeps the original stop end) and `state.wire2` the one before it (ends at the loop's stop point), so the loop is set as `wire1`'s START-end sibling and `wire2`'s STOP-end sibling; it used to be set on the opposite ends, overwriting the original far-end sibling (a terminal or splice) in memory until a reload rebuilt the graph. Deleting the loop reads the far-end sibling.

#### wire_service_loop_search.pyx

Hand-written Cython (`LoopSearch`) holding the whole roll/slide search in C: quaternion twist and matrix, no `Angle`/numpy per pose (~0.55 us per box-only pose). **Two stages per candidate** (the user's design, 2026-10-25): (1) the HIT LIST: an oriented-box separating-axis test behind an axis-aligned reject (conservative, a coil does not fill its box); (2) the MESH stage, only for boxes that overlap: the loop's own mesh vertices (~30,000, indexed once in a cached 10x10x10 grid) against the candidate's real shape — `KIND_CYLINDER` (a wire section's mesh IS a 360-sided cylinder, so the exact cylinder inscribed in its box along the box's z axis, flat ends) or `KIND_BOX` (another loop or a marker: its own box, so tight on our side and still conservative on theirs). A candidate collides only when BOTH stages say so; a wire passing through the coil's hole touches no vertex and is clear. Built once per move session: `LoopSearch(boxes, kinds, local_obb, scale, loop_vertices)`; `search(p1, p2, pivot, axis, q0, t0, pos_limit, neg_limit, slide_step, roll_deg, slide_roll_deg)` takes the per-call inputs (the loop's current start/stop points and angle, the wire's axis and the pivot) and returns `(t, theta_deg, (w, x, y, z), start, stop)` or `None`: the NEAREST clear roll at the current spot in `roll_deg` steps (+k then -k outward; both clear at one distance: less contact at the first step wins, equal: +), else the same scan at each slide position in the coarser `slide_roll_deg` steps, closest slide wins. `pose_at` is the pure maths (pose after a roll and slide) for checking; `is_clear`, `contact` and `boxes_overlap` (stage one alone) exist for diagnosis. The rotation is documented in the module docstring ("Rotation: about the WIRE, through the pivot"). The loop's scale must be uniform (a cylinder has to stay a cylinder in the loop's frame). Its rotation matrix is `Angle.as_matrix_numpy`'s column-vector `R` (the loop's box axes are its COLUMNS). It has NO pure-Python fallback (the user's "No fallback paths" rule): `wire_service_loop.py` imports it directly, so the compiled `.pyd` must sit beside it (gitignored; rebuild after every edit, recipe in MEMORY.md's "Cython extensions" entry) and it is registered in `builder/cython_build.py`'s `_HAND_WRITTEN_EXTENSIONS`. A box that is flat in any axis falls back to its own axis-aligned bounds (and to `KIND_BOX`); touching counts as a collision. **The real boxes are FLOAT32** (`Point.as_numpy` and `Angle.as_matrix_numpy` are float32, so `Wire.segment_obbs` computes in float32): a `KIND_CYLINDER` box is square across x and y only to float32 noise (2e-6 mm at 50 mm from the origin, 8e-5 mm at 2 m), so the constructor accepts a difference of up to 1% of the radius (radius = the mean of the two widths) and raises `ValueError` beyond that. A tolerance tighter than that raised on the first real run.

#### Objects3D context menu architecture
Key conventions (learned 2026-06-11 while completing the objects3d context menus):
- Every scene item is an `ObjectBase` (`objects/object_base.py`) with `.obj2d`/`.obj3d` children; `Base3D.parent` points back to the ObjectBase. Menus receive the Base3D as `self.selected` (HousingMenu uses `self.obj`); ObjectBase-level ops (select, clone, rotate menus) must use `.parent`.
- Shared menu callback helpers live in `harness_designer/objects/objects3d/menu_ops.py` (select/clone/delete/properties/trace_circuit/start_handler/run_attached_handler/get_part_id).
- Interactive placement flows are `harness_designer/handlers/Add*Handler(mainframe, ...)`; the toolbar installs them via `MainFrame._on_tool_mode_change`; context menus use the public `MainFrame.set_obj_handler()` (added 2026-06-11). Housing-attached handlers (Seal/CPA/TPA/Cover with a housing arg) create the db object in the constructor — finalize with `capture_position(...)` + `release_capture()`.
- Object creation = insert into `project.ptables.pjt_*_table`, wrap in `objects/<type>.py` class, register with `project.add_<type>(obj)`. Deletion = `project.delete_<type>(db_id)` (pops registry + deletes db) plus `mainframe.remove_object(parent)`.

#### Cavity 3D angle binding
Bind the 3D cavity object to `db_obj.angle3d` (the project cavity's world-space angle), NOT `db_obj.part.angle3d` (the global baked part angle). Using the project angle makes the cavity visually follow housing rotations.

Do NOT override `_update_angle` or `_update_position` in `objects3d/cavity.py`. Those overrides propagate deltas to the terminal — combined with the project angle binding, they create a callback chain that fires during project loading (before all objects are initialized), causing the app to freeze. `Base3D._update_angle` handles everything correctly on its own once the right angle is bound.

**Why:** The global part angle never changes when the housing rotates, so cavities stayed in their baked orientation. Switching to project angle fires `Base3D._update_angle` directly via the existing housing rotation callback chain. The overrides existed to propagate deltas to terminals, but with the project angle this delta propagation during loading caused a freeze.

**How to apply:** In `objects3d/cavity.py` `__init__`, pass `db_obj.angle3d` (not `db_obj.part.angle3d`) to `Base3D.__init__`. Don't add `_update_angle`/`_update_position` overrides. Terminal delta propagation is handled at the DB layer by `pjt_cavity._update_angle3d`.

#### Wire service loop: lasting rules (built 2026-10-25/26, user-directed)
Files: `objects/objects_3d/wire_service_loop.py`, `wire_service_loop_search.pyx` (+ `.pyi`), `drag_handlers/editor_3d/wire_service_loop.py`, `rotation_handlers/.../wire_roll.py`, `handlers/wire_topology.py`. Only the collision roll/slide was confirmed in the real app (fast, rolls around whatever it hits); the rest was run against fakes only.
- **Geometry and length:** the mesh (`shapes/cylinder_helix.create_vbo`) is a one-turn helix whose centre track has radius = 1 wire diameter (coil ID 1x the wire, OD 3x), pitch 1.15 d, plus two straight leads of 1 d each. `length_mm` = one turn along the centre track + `diameter * 2.0` = 8.39 x OD, computed from the wire diameter with no constants; weight, resistance and editor totals follow it. If the mesh changes, change `length_mm`, bump `_MESH_CACHE_VERSION` and redo the hand-tuned second-lead offsets.
- **Local frame (matrix columns):** +X = the coil's axis, +Y = the loop's diameter (top), +Z = the leads (front). The helix endpoint (1.115, 0.037, -2.169 wire diameters) lies BEHIND the start along the wire.
- **Topology:** the wire before the loop ends at the loop's STOP point; the wire after it starts at the loop's START point. `_wire_points` and every merge/ordering depends on this, and a silent early return on the wrong order once killed the whole roll/slide feature unnoticed.
- **Collision is box-first, never mesh-vs-mesh** (that took 6 s and ~0.5 GB per test and froze the app). A wire's pool OBB is the envelope of all its sections, so use `Wire.segment_obbs()` (one OBB per section, pool corner order). The compiled `LoopSearch(boxes, kinds, local_obb, scale, loop_vertices)` is built in `begin_move_session` (cached in `_MoveSession.loop_search`): stage 1 separating-axis box test is the hit list, stage 2 tests the loop's ~30,000 vertices against the candidate's real shape (`KIND_CYLINDER` for wire sections, `KIND_BOX` otherwise). No fallback path: a checkout without the `.pyd` fails at import. The `.pyd` is gitignored, so rebuild after edits and on a fresh checkout; a running app locks it (ask the user to close the app, never force). A cylinder box is square only to float32 noise, so the check allows 1% of the radius.
- **Roll about the WIRE, not the start/stop line** (the start/stop line is 27 degrees off the coil axis, so rolling about it wobbles). Axis = line through the points either side of the loop (`_wire_points`, waypoints count); pivot = where it meets the start/stop line (`_wire_pivot`; parallel lines use the start point's foot). A roll is the rigid rotation Q about the axis through the pivot of the mesh AND the start/stop points, and the angle written back is `Q (x) R0` (roll AFTER the current angle, world axis). `LoopSearch.pose_at` holds the maths; `_implied_stop` is the stop point the mesh implies (`_p2` can be stale mid-move). Search: nearest clear roll in 2 degree steps outward (+k, -k; tie goes to the lower contact count, then positive); none clears -> slide along the wire and scan the full turn at each position in 6 degree steps (`_SLIDE_ROLL_STEP_DEG`, the one place a gap under 6 degrees can be missed), closest slide wins. It finds the nearest clear angle, not a physically reachable path. With no wire on both sides (project loading) `_resolve_collision` does nothing. A box nested wholly in the coil's hole counts as clear; other loops/markers are still tested as their box.
- **Rotation rings:** ordinary rings are centered on the loop's centroid (`WireServiceLoop.centroid`, a gizmo Point) because `_update_angle` turns the loop about its centroid by moving the start point. `reposition_all` also compares the centre (`_last_center`) so baked ticks follow. "Rotate on Wire" (context menu, disabled without `can_roll_on_wire`) -> `start_wire_roll` -> `WireRollRings` -> `editor_3d/wire_roll.WireRollRings3D` (single Z ring on the wire pivot, perpendicular to the wire, private `Angle`; roll applied via `roll_to` from the frozen starting pose, no collision search). Ring size is the farthest corner of the loop's box from the pivot x2, my choice rather than the user's figure. Not checked: Escape; changing the loop while the ring is up does not move the pivot.
- **Lock to Wire** (checkable menu entry, not saved): `Base3D._create_drag_handler()` returns the loop's own handler, which projects the mouse delta onto `slide_axle()` and calls `slide_along_wire`. At a bend the loop HOPS: when its leading end is within the stop gap of a waypoint it is turned by the bend and set down `2 * gap` past it (hysteresis), the waypoint moving between the two wires' `'3d'` routes. The gap is half the loop's extent along the wire (`abs(dot(stop - start, axle))`, ~3.25 mm for a 3 mm wire), my reading of "1/2 the length of the loop". A hop needs a waypoint not tagged to a bundle/transition, on no other wire's route, free per `WireLayout.can_drag()`, no U-turn, and a next stretch of at least `3 * gap + length`; it stops at a shared waypoint or at a wire end. Markers are passed, not obstacles, and no collision search runs during the slide. 2D and peg-board routes are untouched by a hop.
- **Euler is the permanent rotation format.** Converting FROM Euler is fine; only conversion TO Euler hits gimbal lock, so never use `Quaternion.as_euler` except for cached Euler. `Angle.from_quat`/`from_matrix` have no Euler cache, so copying `as_euler_float` wrote NaN (the ordinary rings then drew only the Y ring). `_angle_from_quat` builds targets with `_frame_euler` (read off the loop's frame, seeded with the current Euler to choose between the two triples and hold the roll when the front is straight up/down; `_GIMBAL_EPS = 3e-4`). 4 of the 5 loops in the user's saved project have `angle3d = [0,0,0]` with a non-identity `quat3d` (not investigated).
- **Deleting a loop:** `handlers.wire_topology.merge_wires(project, first, second)` takes the wire BEFORE the junction first (the one whose stop is there); the loop's start sibling is the wire AFTER, so the order is easy to get backwards. Loop deletion and `restore_wire_from_split` use `merge_wires_in_place(wire_before, wire_after)`: no point row is deleted, `wire_after`'s route rows change `wire_id`/`idx` (tags survive, unlike `set_route`), markers and the far-end sibling follow, the emptied wire is deleted, the schematic re-routes once. The loop's own points are left as orphans (sweep pending, TODO.md). `_teardown_preview` must run the restore BEFORE the loop's `delete()` or the wires merge twice.
- **Scratch-harness lessons:** feed the code what the app feeds it (float32 `Point.as_numpy`/`Angle` matrices, scenes hundreds of mm from the origin, real `Point`/`Angle` objects, the real `@_check_types.do` methods; set `HARNESS_TYPE_AUDIT_DB` to the scratchpad), build scenes from the user's saved project rather than from reading the code, and check that the harness reaches the feature (a scene with the wrong topology agreed with the bug). The app's Decimal-based `Angle` code is slow: keep sweeps small and write long runs to a file.
