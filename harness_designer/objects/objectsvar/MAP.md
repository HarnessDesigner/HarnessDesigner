## FILES

#### __init__.py

Package init for the common ancestor of every per-view renderable object base class. CODEBASE_MAP.md barely mentions this directory (one passing reference as a consumer of the `ShaderProgram` singleton); in reality it is the shared foundation all three views' own base classes build on. Despite the name, this is not "variant" objects or an alternate/experimental object system — it's the one real base every view's own base class inherits from. If a bug reproduces across all three views identically (not just one), check here first before assuming it's duplicated across `Base3D`/`BaseSchematic`/`BasePegboard` independently.

#### base_var.py

`BaseVar` — view-agnostic object behavior shared by `Base3D` (`objects_3d/base_3d.py`), `BaseSchematic` (`objects_schematic/base_schematic.py`), and `BasePegboard` (`objects_pegboard/base_pegboard.py`), all three of which subclass it directly (confirmed via `dep_trace.py --overrides`). Owns: position/angle/scale properties and their `_update_position`/`_update_angle`/`_update_scale` hooks (each view's base class overrides these for its own geometry/VBO handling); OBB/AABB computation (`_compute_obb`/`_compute_aabb`) and the ray-triangle hit-test pipeline (`hit_test_step1/2/3`, `_ray_triangles_intersect_vectorized`); selection state (`is_selected`/`set_selected`), visibility (`is_visible`), and material/color resolution (`material`, `_selected_color`, `selected_material`); drag/rotate gating and dispatch (`can_drag`/`drag`, `can_rotate`/`rotate`, `handle_interaction`, `handle_wheel`); the generic render surface (`render`, `render_selected_overlay`, `render_handler`, `_render_geometry`) that takes a `ShaderProgram`-family `Program` instance and sets uniforms only through its typed properties, never raw `GL.glUniform*` calls (see `gl/shaders/`'s `program.py` in CODEBASE_MAP.md for the full convention this follows); and `try_pick_cavity`, stubbed here (returns `None`) and meaningfully implemented only on `Housing3D`/`Cavity3D` (3D view). Because `BaseVar` already implements `_update_position`/`_update_angle` generically, **don't reintroduce redundant override logic in a per-view base class** unless that view genuinely needs different geometry handling — see the cavity-angle-binding entries in MEMORY.md for a real case where an unnecessary 3D-specific override (`objects_3d/cavity.py`) caused a project-load freeze; `Base3D._update_angle` (ultimately `BaseVar._update_angle`) handles it correctly on its own once the right angle is bound.
