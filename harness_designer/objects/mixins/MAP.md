## FILES

#### __init__.py

Package init for the view-agnostic wrapper-level mixins, shared across `objects/<type>.py` modules (not the per-view `objects_3d`/`objects_schematic`/`objects_pegboard` renderables — see those packages' own mixins for the per-view wire mixins).

#### wire.py

`WireTypeMixin` — the view-agnostic base of the wire-type mixin hierarchy: `_waypoints`, `_point_on_wire`, `_endpoint_diameter`, `_segments`, `get_closest_point`, `get_closest_endpoint`. `objects_3d/mixins/wire_type.py`'s `WireTypeMixin` and `objects_pegboard/mixins.py`'s `WireTypeMixin` both subclass this one and override `_waypoints`/`_point_on_wire`/`_segments` with view-specific geometry (ray-vs-segment for 3D, 2D xz-plane closest-point for peg-board); there is no schematic counterpart (`objects_schematic/mixins/` is empty). Two unrelated classes in this codebase share the bare name `WireTypeMixin` (this one, plus the 3D and peg-board subclasses) — not a bug, just worth knowing before grepping by name; `dep_trace.py --calls`/`--overrides` resolves them correctly since it builds a real class hierarchy, but a plain-text search returns three unrelated-looking hits.

#### tube.py

`TubeMixin` (NEW 2026-11-08, moved out of `objects_3d/wire.py` where the 3D wire kept it, `WAYPOINT_REWORK_DESIGN.md`): how a wire, cable or bundle is drawn, in every view. `_init_tubes()` (plan, pool key and rows, batch entries), `_make_look` / `_build_twist` / `_build_single` / `_active_look` / `_single_radius` (the look: twisted, ribbon, or one plain tube), `_conductor_materials`, `_segment_joins`, `_twist_segments` (the path cut into pieces with its corners rounded by `shapes/twisted_path.build_path`, cached per look and packed into pool rows), `_curve_chords` (the path as drawn, for the waypoint preview), `_render_tubes` (visibility, bounds marking for picking, then `_batch_wire`), `_write_pool_rows`, `_batch_wire` (hands the canvas one entry per conductor). Also `TwistLook` and `TwistSegment`. **Floor outline (2026-11-08):** a selected wire, bundle or cable casts the OUTLINE of its path as seen from above (the drawn, rounded path, a tube wide, flattened along Y) onto the floor, in `Config.debug.rendering3d.floor_projection_color`, a fixed line width of `floor_projection_width` mm (1.5 by default, not based on the diameter; both are config settings, not in the Debug Settings dialog): `TubeMixin._render_floor_outline`, called from `render_selected_overlay` after the waypoint overlays, using `gl/floor_outline.py`. The old rectangle per section is off for these classes (`Base3D._floor_projection_enabled = False`; every other object keeps its OBB footprint). **Bare conductor ends (2026-11-08, back after the rework):** a ONE-conductor wire whose first / last sub-segment crimps into a Terminal (`TubeMixin._conductor_segment_ends`, the sibling graph) draws the straight piece cut from that segment as the bare conductor (`conductor_dia_mm`, the core's polished metal, no stripe, not when selected); a wire of one piece is bare throughout when either end crimps. It is an ENTRY of its own over a sub-range of the wire's rows (entry texel 9 = where the range begins in the wire's own draw, `gl/wire_batch.entries_for(..., rows, ends)`), so the wire stays one pool allocation. The arc chords of the rounded corner next to it keep the insulation. Twisted pairs and cables never have bare ends. Hooks: `_has_bare_ends` (True on the wire classes), `_bare_ends`, `_bare_conductor`. The class supplies `_segment_transforms()`, `_part`, `_material`, `_selected_material`, `_stripe`, `_twist`, `_trunk_size` and the BaseVar bounds. Used by the 3D and pegboard wire, cable and bundle.

**Ray tracer (2026-11-08):** `ray_trace_meshes()` yields `(vertices, normals, material)` for every conductor and its stripe, from the same plan the viewport draws (`_twist_segments`, `_active_look`), through `ray_tracing/tube_mesh.py`: rounded corners, twist, mitres, smooth normals, the bare ends of a wire that crimps into a terminal and, selected, the selection material with no stripe, exactly as `_batch_wire` chooses them. `Scene.add_object` calls it on the GUI thread (it makes no GL call).

**A path with no length (2026-11-10):** `_render_tubes` returns without drawing when the packed path has no rows (both ends of the wire on one spot) and logs one warning per wire (`_reported_empty`); `WirePool.set_rows` raised `vertex_count must be > 0` on every frame and wrote a render failure report each time. This only stops the error: why a new piece of a split wire had both ends on one spot when it was first drawn (seen for the pieces a wire service loop makes, in both views) is not found.

#### waypoint_handles.py

`WaypointOwnerMixin` plus a small registry (NEW 2026-11-08; reworked the same day): a waypoint is not an object of its own to see or pick, its wire / bundle / cable drags it. While the owner is selected its waypoints are drag handles: a sphere `HANDLE_SCALE` (1.25) times the diameter, centred on the point of the DRAWN path (rounded corners) nearest the waypoint, since the tube passes inside the corner (`_handle_centers`). `_handle_hit` (called from the owner's `hit_test_step3`) makes the owner pickable over a handle; `_arm_waypoint_drag` (first thing in the owner's LEFT_DOWN, `_handle_waypoint_drag` first thing in every event while armed) arms the drag the view's `_make_waypoint_drag` builds (3D: `Generic` through the layout's data object with the owner sizing the arrows, or `drag_handlers/editor_3d/waypoint.py` for a cable, which has no layouts; the board: `Generic` through the layout object) and never changes the selection; `delete_closest_waypoint` is the menus' **Delete Layout** (the waypoint nearest the right click: the layout is deleted, a cable removes its own point). The registry (`register`, `layout_for`) maps a waypoint's point id to the layout object at it; `preview_geometry()` / `wants_preview_geometry()` give the preview of a waypoint being placed its sphere. **No layout geometry (2026-11-08, `WAYPOINT_REWORK_DESIGN.md`):** a layout's view object is data only (a position and the row the routing logic reads): it has no vbo, so it is never drawn, never picked and not a ray-traced object. Only the cable's split markers, the wire placement flow's snap probes and the preview sphere of a waypoint being placed (`preview_geometry()`, ended by `end_preview()`) keep a sphere. A waypoint is dragged and deleted through its wire / bundle / cable (`objects/mixins/waypoint_handles.py`), which finds the layout's object by point id and runs the same `Generic` drag on it.

**Saving a move (2026-11-08):** a point writes its moves back to its database row through a weak callback, so a waypoint's move is saved only while something holds the row. A waypoint with a layout is held by it; a cable's has none, so every `_bind_waypoints` (3D wire, which the cable inherits, 3D bundle, board wire) keeps its rows in `_waypoint_rows`, and `drag_handlers/editor_3d/waypoint.py` holds the row of the point it drags. Without that a cable waypoint's new position was never written.

**Delete (2026-11-08):** `_delete_waypoint` deletes nothing for a waypoint whose layout cannot be dragged (a terminal's or cavity's routing point, one shared with a boot or a transition). The board's wire, bundle and cable menus have **Delete Layout** too; the board cable (no layouts) removes its own point from `pjt_cable_paths` (`'pegboard'`).
